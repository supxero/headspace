# Headspace, technical review

State of the code as of the commit that reworked the Notes view into a real writing surface: a bounded-measure page editor that grows with its text, a quiet edited/word-count meta line, search across titles and bodies, display-sort by last edit, and a pin flag riding the pos axis (2026-08-10). Written for a reviewer who has not read the file. Line numbers refer to `index.html` at this commit and will drift; section names and function names are the stable handles. This is a critical review, not a status report: the Weak points and Risk list sections are the ones to read first.

## 1. Structure

One file, `index.html`, 3363 lines: CSS to line 667, static HTML to 726, then one `<script>` to the end. No modules, no build. `sw.js` (36 lines) is a cache-first service worker keyed on a manually bumped `CACHE` constant. State flow: every mutation goes `handler mutates state -> save() (400ms debounce) -> commit() -> stampChanges() diff -> localStorage -> pushSoon() (1800ms debounce) -> syncCycle()`. Rendering is full `innerHTML` rebuild of each region on every `render()`.

Grown unwieldy:

- The delegated click handler (`index.html:2503`) is ~330 lines and 79 `case`s with two exit conventions: `return` means the case handled its own save/render, `break` falls through to a shared `save(); render()`. Picking the wrong one is an easy, silent mistake, and the pre-switch block that closes the inline add field (added for the mobile trap fix) runs a deferred `save(); render()` in a `setTimeout(0)` that has to guess whether a rename just started by sniffing `document.activeElement.dataset.kind`. It works and is tested, but it is the most fragile control flow in the file.
- `render()` re-renders everything on every action. Fine at current data sizes, but it is why focus/caret preservation needs manual bookkeeping (`ui.adding`, `ui.addText`); any future input element gets the same class of bug until someone remembers that. One concrete cost, observed during the four-profile input verification: while any inline rename is open (task, tab, habit, weekly item, and the rename `float-new` auto-opens), the first tap on any other control is spent on the rename's blur, whose commit re-renders the tree under the gesture before mouseup lands, so that tap does nothing and the user must tap again. Pre-existing, affects every rename path equally, and inherent to commit-on-blur plus full re-render; noted here rather than patched. The Notes editor was checked against exactly this and does NOT make it worse: its title and body are a real input and textarea that write state on every `input` event through the save debounce, nothing commits on blur and nothing re-renders on a keystroke, so the first tap out of the editor lands (pinned by a test). What it does inherit is the foreign-re-render case: a render arriving from elsewhere (sync adopt, the midnight check) rebuilds the fields, so `renderNotes` restores focus and caret by hand, the same bookkeeping `ui.adding` needed; since the Notes rework the search box is a third such field, restored the same way with its query (`ui.noteQ`, memory-only) and its caret. Typing in the search box re-renders nothing at all: it patches `#noteRows` in place, calls no `save()`, and so can never steal focus from the editor or reset a caret mid-word (pinned by tests in both suites). The tab-drag polish was checked against the same first-tap cost and moves it in neither direction: while any rename is open, the press that would begin a drag elsewhere is spent on the blur, whose commit re-render replaces the pressed header before the browser's drag threshold is met, so the drag needs a second press exactly as a tap needs a second tap. The polish adds no press-time listeners (dragstart and its open-rename guard are untouched), and the FLIP runs only on a completed drop, which cannot coincide with a pending blur since the blur resolves at the drag's initial press.

## 2. State shape

```
state = {
  ver: 2,
  days:   { "YYYY-MM-DD": { must:[Task], should:[Task], extra:[Task] } },
  carry:  [Task],                    // + .from label on carried tasks
  focus:  [{ id, title, done, doneAt, up }],   // True north statements; done+doneAt now mean "set aside" + "held until"
  floats: [{ id, name, tasks:[Task], up }],
  tomb:   { id: msTimestamp },       // deletions, kept 45d (TOMB_KEEP)
  bin:    { id: { k:'task'|'sub'|'float'|'focus'|'habit'|'wtask', at, body, loc?, pid?, pname?, moved?, purged? } },
  habits: { list:[{ id, name, days:[1..6], up, dn, pos }],   // Mon=1 .. Sat=6, no Sunday
            marks:{ "mondayISO": { habitId: { dow: +-msTimestamp } } } },
  week:   { list:[{ id, title, done, up, dn, pos }],         // flat, no tiers, no days
            hist:{ "mondayISO": [{ id, title, at }] } },     // weeks already closed
  notes:  [{ id, title, body, pinned?, up, dn, pos }],       // plain text; pinned rides pos
  settings: { view, boardOffset, floatMode, activeFloat, calSel, calOffset,
              mRange, stripDay, lastRoll, showDone, habitsOpen, lastWeek, noteSel }
}
Task = { id, title, done, subtasks:[{id,title,done,up,dn,pos}], up, dn, pos, from? }
```

Every mergeable item carries **three** stamps, merged independently (Section 3):

| Stamp | Covers | Declared in |
|---|---|---|
| `up` | title, a tab's name, a note's title, or a habit's name and active days | `CONTENTF`, `sigC` |
| `dn` | `done`, a focus item's `doneAt`; for a habit no fields, only the moment its marks last changed; for a note the entire `body` | `DONEF`, `sigD` |
| `pos` | location, order in its list (tabs and notes included), a task's `from` label, a note's `pinned` flag | `POSF`, `sigP` |

Habit ticks are the exception to items-carry-their-fields: they live outside the item in `habits.marks`, one cell per habit, week and day, holding a timestamp that is positive for ticked and negative for unticked. `mergeMarks()` unions cells and resolves a contested cell by larger absolute value, so a Monday tick on one device and a Wednesday tick on another can never conflict, which is the property the item's single `dn` stamp could not give. The habit's `dn` still moves when its marks change (`sigD` hashes them via `marksSigFor`), carrying no fields; it exists only so ticking a habit asserts it should exist against a concurrent delete, the same revival rule tasks have.

**The focus kind was reworked into the True north panel (2026-08-10) without touching its stored shape.** The user-facing name, the tick, the "open" count and the Completed section are gone; what remains is a statement panel whose archive gesture is "set aside". Set aside writes the very same `done`/`doneAt` fields the tick wrote (`doneAt` renders as "held until"), so the `dn` axis, `DONEF.focus`, `sigD`, the merge fixtures and every saved planner carry over with zero migration: an old ticked item IS a set-aside statement and files under the archive with its date. The archive itself is option (b) of an owner decision and is flagged reversible in `renderFocus`; reversing to no-archive means deleting the aside branch of `frow`, the Set aside section and three handler cases, with no data change. The panel is pinned open while it holds a current statement: the header then renders no chevron and carries no toggle action, and since no collapse flag for it is persisted anywhere (peek is memory-only), a planner holding statements can never load collapsed. Only the empty panel (set-aside statements do not count) collapses to its header bar, which reads "not set" rather than a count. Internal names (`state.focus`, the `focus-*` actions, bin kind `focus`, `settings.showDone`) deliberately keep the old word; the only place a user can meet it is the export file's `focus` key, which is the state key that must not change.

A note has no tick, so its `dn` axis carries the body instead (`DONEF.note=['body']`, `sigD` hashes the body): a title edit on one device and a body edit on another then compose instead of one discarding the other. What this does NOT solve, and nothing short of a merge UI or CRDT text would: two devices editing the same BODY resolve by later `dn` wins, whole body, and the older rewrite is silently discarded with no record and no bin entry. That is the same same-field class every item has (Section 3, item 1), but the payload is a body of text rather than a title, so it is called out separately in risk 11 and pinned by a test so it can only change deliberately. Anyone reasoning "dn means done" will misread notes; after this commit the axis really means "the second independently merged channel".

**A note's `pinned` flag rides the pos axis (new with the Notes rework, 2026-08-10).** Pinning says where the note sits (the top of the list), not what it says or what is written in it, so it is classified into `POSF.note` and hashed by `sigP`: a pin toggle bumps only the position stamp, composes with a concurrent title edit (up) and a concurrent body edit (dn), and, exactly like a move, cannot revive a note deleted elsewhere, since tombstones are compared against `up` and `dn` only. It deliberately does NOT touch how a body merges, which was the constraint. The flag is stored as `pinned:true` or absent, never `false`, so exports and old planners stay clean; `flatten` normalises it and `rebuild` writes it back only when set. The notes LIST on screen is a display sort, `noteOrder()`: pinned first, then by `max(up,dn)` (last edit; position moves do not count), ties in stored-array order. The stored array is never reordered by browsing, searching or the sort itself, so reading the list churns no stamps; only creation (`unshift`), deletion and restore still move array positions, exactly as before.

Anything written before a split has only the older stamps; `posOf()`/`dnOf()` fall back to `up`, and `stampLegacy()` backfills both at load, so a split becomes fully active after one save.

Synced vs local:

- **Merged item-by-item:** everything under `days`, `carry`, `focus`, `floats` (tasks, subtasks, tabs), `habits.list`, `week.list`, `notes`, plus `tomb` and `bin`; `habits.marks` merges cell-by-cell as above, `week.hist` by union (`mergeHist`, newer `at` wins a shared id). Weekly items are the plainest kind of all: title on content, `done` on its own dn axis, order on pos, exactly the focus-item shape. Tab order needed no new field at all: it is the floats array order, already stamped on `pos`, so the drag reorder rides the same axis task order always has. `emptyPlanner()` now counts notes as content, so a notes-only device is not silently overwritten by `connectKey`.
- **Device-local under merge:** the entire `settings` object. `rebuild()` (`index.html:951`) takes only `mine.settings`. `VIEWSET` (`index.html:1066`) is used only by the manual-Pull path (`applyCloud`) to keep local view state while importing the rest of the remote settings. So merge and manual Pull treat settings differently; that asymmetry is deliberate but undocumented outside this file.
- **localStorage, never in the cloud blob:** the sync key (`agora_dayplanner_synckey`), agreement stamp (`agora_dayplanner_syncstamp`), pre-pull backup (`agora_dayplanner_v1_backup`).

**Unknown top-level keys now pass through (fixed, was the headline risk).** `rebuild()` still reconstructs the keys it understands, declared in `MERGED_KEYS`, but it ends with `carryUnknown(out, mine, theirs)`, which copies through every top-level key neither side's merge logic knows about. A key added to `state` in future therefore survives a merge instead of being silently dropped. It gets no last-write-wins (there are no stamps for it): whichever side has it wins, and if both differ the smaller JSON wins, which is arbitrary but identical on both devices, so they still converge. `stateSig()` hashes unknown keys too, so a change to one still triggers a push. A test asserts `MERGED_KEYS` still matches `Object.keys(fresh())`, so adding a key to the canonical shape fails the suite until someone decides whether it needs real merge semantics or the generic pass-through is fine.

## 3. Sync and merge

Mechanics: one Supabase row per sync key, whole-state JSON in `data`, publishable API key embedded in the page. `syncCycle()` (`index.html:1258`) runs on boot, focus/visibility, reconnect, a 25s poll, and 1.8s after any edit. It does GET, `mergeStates(local, cloud)`, adopts the merge if it changed anything, and PUTs if the cloud is missing anything, comparing via `stateSig`. The Push/Pull buttons are raw overwrites in both directions (documented in the sync modal); Pull backs up to `agora_dayplanner_v1_backup` and offers toast-undo.

Merge rules: union by id. Per item, **title, tick and position are resolved separately**: the side with the newer `up` supplies the title, the newer `dn` supplies the tick, the newer `pos` supplies location/order/`from`, and `pickNewer()` splices the three together. Equal stamps break by JSON comparison of just the fields under that stamp, so both devices agree. A tombstone kills anything whose `up` **and** `dn` are both older than the deletion: editing or ticking asserts the item exists, moving it does not. `stampChanges()` assigns all three by diffing a structured signature (`{c,d,p}`, no separator to collide with user text) at commit time, so every mutation path is covered without instrumentation. Habit rows ride the same axes, with the schedule (`days`) as content beside the name; their ticks merge cell-by-cell instead (Section 2). The weekly list turns at Monday 00:00 through `weekSweep()`, gated per device by `settings.lastWeek` the way the daily roll is gated by `lastRoll`: ticked items graduate into `week.hist` under the week that closed and leave the tree, so the normal diff tombs them (a stale device's ticked copy cannot bring them back) while `ui.skipBin` keeps them out of the bin, since finishing a week is not a deletion. Unticked items simply stay, which is the carry. A device off for several weeks archives its finished items under the last week it saw, an accepted approximation. Subtasks are not listed in their parent's signature, so adding a step does not restamp the task it belongs to. Bin entries follow their tombstones; purge markers are terminal.

Cases resolved by an arbitrary rule or still able to lose data:

1. **Two edits to the same field: later stamp wins, the loser is silently discarded.** Now genuinely narrow. Rename versus tick is fixed (`dn` is its own axis), as is either versus a move. What remains within edit-versus-edit is same-field-versus-same-field: two devices **renaming the same task** to different text, two **ticking it differently** (an untick after a tick, and the later one wins), two **moving it to different places**, or, new with the Notes view, two devices **editing the same note body**, where the later `dn` takes the whole body and the older rewrite goes without record or bin entry. The note case is the costliest instance of this class, since the payload is paragraphs rather than a title; a title edit against a body edit composes fine (separate axes), body against body has one loser. One side loses, with no record and no merge UI. Renaming two *different* tasks, or renaming one while ticking or moving it, all survive intact. Delete conflicts have losers of their own, item 4.
2. **Reorder vs content edit, and rename vs tick: both fixed.** The signature was split three ways (`sigC`/`sigD`/`sigP`) with a stamp each. A reorder bumps only `pos`, a rename only `up`, a tick only `dn`, so none can discard another, in any direction, and all three compose on one task at once. Tested fourteen ways, including every mirror case and convergence. Reverting either split fails six assertions each.
3. **Move vs rename: fixed** by the same split. The task lands in the newly moved-to place carrying the newly typed text.
4. **Edit or tick after delete resurrects** (deliberate, tested). Ambiguous case: the stamps and the tomb are compared across devices with unsynchronized clocks. **A reorder or a move no longer resurrects a deleted item**, since the tombstone is compared against `up` and `dn` only; editing or ticking asserts the item should exist, shuffling it does not, and pinning a note is shuffling, not editing (pinned by a test in both merge directions). **Revival is strictly per item: work on a subtask does not defend its deleted parent.** Delete a task on one device while another ticks one of its steps, or adds a brand new one, and the steps die with the parent, silently, with no bin entry anywhere in the merged state; `rebuild()` drops any surviving step whose parent was not kept ("never orphan a step", `index.html:970`), even a step whose own `dn` beat the tombstone. Conversely a parent revived by its own rename comes back with zero steps, since its old steps were tombed individually and nothing re-asserted them. Pinned by tests in both merge directions, including the no-bin-entry fact and the parent-rename contrast.
5. **Clock skew skews everything.** All conflict resolution is `Date.now()` comparison. A device minutes fast wins conflicts it should lose. Nothing detects or compensates.
6. **No optimistic concurrency on the row.** Two devices can GET the same cloud state, merge, and PUT; the second PUT overwrites the first. Nothing is destroyed locally, and the next cycle re-merges and re-pushes, but the cloud can be transiently missing one device's changes, and a device that stops syncing right after losing that race leaves the cloud stale.
7. **Expiry horizons:** bin bodies 30d, tombstones 45d. A device offline more than 45 days resurrects its stale copy of deleted items as "edits after delete".
8. **`emptyPlanner()` ignores `tomb` and `bin`,** so a device whose planner is all-deleted counts as empty; `connectKey` will then adopt the cloud wholesale and discard the local bin bodies.
9. **Restore vs permanent-delete race:** restore wins the item, purge only strips the stored body. Deterministic, but chosen, not derived.
10. **Carry-over tray, observed in Chrome 2026-08-10.** An automatic merge cannot empty or hide the tray: verified against a cloud copy predating rollover and against one with `carry:[]`, the locally carried items win both times. **Exception A is now fixed** by the content/position split: a task rolled into the tray here and renamed on another device after midnight keeps its place in the tray, picks up the rename, and keeps its "Prio 0 · Sun" origin label, because `from` is positional and the rename only moves the content stamp. Pinned by a test. A manual **Pull** still empties the tray by design, restoring the tasks to their day columns, with Undo in the toast.
11. **The once-per-day gate is now visible rather than silent.** `rollIfNewDay` still returns immediately when `settings.lastRoll === today()`, so anything landing on a past day after today's sweep is not swept automatically, which is deliberate: continuous sweeping would fight a user who back-dates a task on purpose. What changed is that the board nav now renders a button reading "N waiting on past days" whenever unfinished tasks sit on past days (`pastOpenCount()`), and pressing it runs the sweep on demand, stamped now rather than at midnight since it is a deliberate act. The gate's behaviour is asserted by a test driven through `rollIfNewDay`, not `rollover`, so it cannot change silently.
12. Manual Push/Pull remain whole-blob overwrites; a habitual Push from a stale device wipes cloud-side items until another device's next merge re-uploads whatever it still holds (items deleted only in the cloud copy come back; items only in the cloud copy are gone for good unless another device holds them).

## 4. Known weak points

- **`ui.skipBin` / `ui.binNote` are side-channels** between three click-handler cases (`spop`, the two drag-conversion branches, `float-del-move`) and the next `stampChanges` run, carried in mutable `ui` fields and cleared unconditionally per commit. If an unrelated commit fires inside the 400ms save debounce (e.g. a sync `adopt()`), the flags are consumed by the wrong commit: worst case a popped-out subtask also shows up in the bin as a "deleted" step. Low probability, unhandled, untested. (`ui.drag`'s new `over`/`rect`/`side` cache is not in this class: it lives and dies inside one drag gesture, is cleared by dragend, and never reaches a commit or the serialized state.)
- **`prevSnap`** (the deep copy backing `binCapture`) must be refreshed by every path that swaps state; today `load()` and `commit()` do it and `adopt()` gets it transitively via commit. A future state-swapping path that forgets will produce bin entries with wrong or missing bodies, silently.
- **Three stamps per item now, and all three must be maintained.** `stampChanges` writes `up`, `dn` and `pos` from a three-part signature; a future field added to an item must be classified into `CONTENTF`/`DONEF`/`POSF` (used by `pickNewer` for tie-breaks) *and* into `sigC`/`sigD`/`sigP` (used to decide which stamp moves). Miss the signature and the field never triggers a stamp, so edits to it silently lose merges. Nothing enforces the pairing; a test that round-trips every field through a merge would. The habit kind adds a twist: its `sigD` reads the item's marks through `eachItem`'s meta (`marksSigFor`), so the dn stamp depends on state outside the item itself; anyone adding a second such out-of-item signal must remember to thread it through the meta the same way. The note kind bends the axes the other way: `dn` carries no tick but the whole body, and since the True north rework the focus kind's `dn` means "set aside", not completion, so the axis names no longer describe their cargo for every kind; the tables in `CONTENTF`/`DONEF`/`POSF` are the truth, not the names. The note's `pinned` flag is the newest worked example of the pairing done right: it sits in `POSF.note` AND in `sigP('note')`, so a pin toggle both restamps and wins ties on exactly one axis; miss either half and pins would silently lose merges, which is precisely the trap this bullet warns about.
- **The custom picker layer has two contracts nothing enforces.** On hover:hover devices a popover replaces the native date popup and the `#qd` dropdown (the natives are unstylable and OS blue); the native inputs and all their handlers stay untouched, the popover writes `value` and fires the same bubbling `change`. Contract one: while a popover is open, a capture-phase keydown handler owns Enter, Space, arrows, Escape and Tab and stops propagation, so a future global key feature must check the layer's `pop` state or it will never see those keys. Contract two: a capture-phase click handler swallows clicks on the three anchor controls (the `pickdate` input carries a `data-action`, and its raw click used to fall through the delegated switch into a stray `save()+render()` that closed the popover through the board scroll reset), so giving those anchors real click behaviour in the delegated switch will silently not work on desktop. Both contracts are pinned by tests. A third choice is deliberate: after a mouse pick the date input is left unfocused, since Chrome paints the focused segment highlight in OS blue and no CSS reaches it; keyboard flows do restore focus, and that highlight is then the focus indicator.
- **Two-field board position** (`boardOffset` for wide, `stripDay` for narrow) still exists; `shiftBoard()`/`showDay()` keep them in step at the five current call sites, but `windowDays()` (`index.html:1822`) still branches on `window.innerWidth<900`, so any new navigation control must go through the helpers or it will regress exactly like Prev/Next did on iOS.
- **`paintBin()` is called from `commit()`**: a DOM write inside the persistence layer, because renders don't run on commit. Works, but it is the only place data-layer code touches the DOM besides the save badge, and it will confuse anyone refactoring commit.
- **Copy rules are enforced by habit, not tooling.** No-white / no-emoji / no-em-dash checks live in `visual.py`, which cannot currently run (no Python). Reviews have relied on grep.
- **The cache-bump ritual** (`sw.js` CACHE constant) is manual and unenforced; CLAUDE.md calls it the most common mistake, and nothing in the test suite checks that the constant changed alongside `index.html`.
- **`state.days` is never pruned.** History is the data model (metrics, streak), so this is by design, but `syncCycle` runs `flatten`+`stateSig` up to three times per cycle, every 25 seconds, over everything ever created. Years of data on a low-end phone will make the poll visibly expensive.
- **Quota/private-mode handling is a toast** ("not saving") plus in-memory operation; `sync.pending` is memory-only, so a kill while offline loses nothing (merge recovers) but a kill mid-typing loses the debounce window (up to 400ms of edits). The Notes editor widens that window: it calls `save()` on every keystroke and each call resets the 400ms timer, so typing that never pauses defers the commit for as long as the typing runs. Any pause, blur, tab switch or close flushes it (`visibilitychange`/`beforeunload` commit), so the exposure is a hard kill mid-sentence, losing back to the last 400ms pause rather than a bounded 400ms. The Notes rework changes none of this: title and body keystrokes ride the same per-input `save()` they always did, the meta line and the list row are patched in place without touching the save path, and the search box calls no `save()` at all, since the query is `ui`-only and nothing about searching persists.
- **Quick patches acknowledged as such:** the `setTimeout(0)` outside-tap logic in the click handler (Section 1); `binWhere`'s guards for malformed `loc` return vague labels rather than validating entries on write; `restoreBin` re-uses ids on restore (safe today because revival clears tombs, but it means id uniqueness across time is not an invariant anyone can rely on); and the import path stamps only `up` when it adopts a file, so an import asserts titles and schedules as the newest word but not ticks, and now not note bodies either, since those ride `dn`, nor pins, since those ride `pos`. A body edited on a live device after the export therefore survives an import of the older file, which is arguably the right outcome but is not what the comment beside the import promises.

## 5. Regressions and history

- **Mobile inline add trap** (fixed `b6f9c50`): root cause was the resize handler rebuilding the board when the soft keyboard opened. Actually fixed: resize now re-renders only on width change, typed text lives in `ui.addText`. Residual: a *real* width change (rotation) mid-typing still rebuilds; text survives, focus is restored, but the keyboard may flicker. The underlying innerHTML-rerender architecture that caused it is unchanged.
- **Devices overwriting each other** (fixed `33134a3`): whole-blob last-write-wins replaced by the per-item merge. Actually fixed and heavily tested; residual ambiguities listed in Section 3.
- **iOS Prev/Next dead** (fixed `68df415`): not iOS at all; `nav` wrote `boardOffset` while narrow layouts read `stripDay`. Fixed properly at the cause (`shiftBoard`/`showDay`), but the dual-field design that made it possible is still there (Section 4).
- **Carry-over tray vanished** (fixed `13b5551`): `rollover()` had only ever run at boot; auto-sync removed the daily restart that masked it. Actually fixed (`rollIfNewDay` on foreground + 60s timer, midnight-dated stamps, `lastRoll` made device-local). Residual: rolling happens only while the app is foregrounded, so the tray appears on next look, not at 00:00; that is an accepted platform limit, not a bug. **Re-verified end to end in headless Chrome on 2026-08-10, not just in jsdom**: seeded an unfinished task on yesterday with a stale `lastRoll`, and at both 390px and 1280px the tray rendered with the right items, kept the finished task on its day, showed correct origin labels ("Prio 0 · Sun"), placed every triage control in the viewport with `elementFromPoint` returning the control itself, and a real click on "Today" moved the task to today's Prio 0. The feature is genuinely working. Anyone reporting it "broken" has almost certainly hit the once-per-day gate (Section 3, item 11) rather than a defect.
- **Per-task date field dead on click** (fixed in the habits commit): tapping the mm/dd/yyyy field in a task's action bar did nothing, on a Free Floating tab and a day column alike, while every other control in the bar worked. Cause: the input carries `data-action="pickdate"`, so its raw click was funnelled into the delegated switch, matched no case, and fell through to the shared `save()+render()` tail; `renderBoard()` rebuilds `#board.innerHTML` unconditionally, so the input was destroyed in the same task that would have opened the native picker. The `tofloat` select had been given a bare `case 'tofloat': return` long ago, which is exactly why "file to" worked; `pickdate` now has the same case. `#jumpDate` was never affected: it carries no `data-action`, so the handler exits before the switch. On desktop pointer devices the custom picker layer had already masked the bug by swallowing the click; the fix repairs the native path phones actually use. Pinned by tests on both controls.
- **Tab delete control missing** (fixed `c21bff6`): never broke; it had shipped with an empty label since the initial commit and rendered at 10x4px. Fixed with a label and a test asserting visible text, plus the same fix applied when the tray's "Free Floating" button was found blank earlier. Two blank-button bugs from the same cause suggests scanning for empty interactive elements belongs in the visual suite; it is not there yet.

Pattern worth naming: two of the five were latent from day one and only surfaced when adjacent behavior changed. The suite now pins each one, but the class of bug (markup present, visually absent; feature keyed to a lifecycle that stopped happening) is what to watch for.

On tablet-1024 specifically: the full wide board renders, no custom popover ever engages (both date fields stay live native inputs, the B fix holds under touch dispatch), nothing requires hover to reach, and every control offers a finger at least 44px.

**What the pass found, and what changed.** Three defect classes, all fixed in this commit:

1. **Both date inputs had no accessible label** (`#jumpDate` and the per-task `pickdate` field render no text and had no aria-label). Both now carry one, and the suite pins every input on the board to placeholder/aria-label/title.
2. **Nearly every control missed 44px on the coarse profiles.** The first run logged 341 under-44 groups at 1024 and 288 at 390: tick boxes 17 to 20px, mini glyphs 18 to 19px, action bar buttons 22 to 27px, nav and modal buttons 28 to 42px, the date inputs 24 to 31px. The fix is a `@media (pointer:coarse)` block, kept last in the stylesheet: controls drawn small on purpose keep their size and grow an invisible `::before` hit overlay; the press-glow classes (`overflow:hidden` clips any overlay) and the native inputs grow to a real 44px; two width-media rules (`#rail .railfoot button` 42px, `.binrow .nbtn` 40px) are re-overridden at 44 because their specificity beats a bare class. Fine-pointer rendering is untouched; on phones the habits grid also gains 3px of row gap.
3. **The overlays themselves misfired on the first try, and the pass caught its own fix.** Symmetric overlays made the rail habit cells reach up into the name-and-tools line at 1024: the audit reported the Days button's centre resolving to a tick cell, and the habit-schedule flow genuinely ticked a cell instead of opening the editor. The rule that fixed it: overlays are biased downward, because a positioned element always beats an earlier sibling's overlay at its own centre, so room taken below a control can never steal the next row's taps while room taken above a dense row can. The suite pins the biased insets.

**The tab drag path, measured** (headless Chrome, five seeded tabs, instrumented prototypes counting document-wide `querySelectorAll`, classList writes, rect reads, region `innerHTML` sets, save and commit; three runs each side, counts identical every run). A 120-event dragover sweep across the board: before, 70 document-wide queries and 72 class writes, one of each per event that sat over a valid target, whether or not anything had changed; after, 0 queries, 15 class writes (only when the target column or landing side actually changed) and 3 rect reads (one per new target, then cached on `ui.drag`). A 60-event stationary hover, which browsers really do stream: before, 60 queries and 60 writes for zero visual change; after, 0 queries and 2 writes, the initial cue. The drop itself was already single-shot and stays so: one state write, one `save()`, one commit, one render (11 region `innerHTML` sets); the FLIP adds 10 rect reads at the drop, the measure-invert cost, paid once per drop rather than per event. Wall time over the sweep is noise-level either way at this DOM size (2 to 3ms per 120 dispatches, dominated by event dispatch); the change is that per-event cost no longer includes a full-document query, so it stops scaling with the size of the rendered tree.

**Noted, not fixed.** Opening the bin within the 400ms save debounce of a deletion shows a list without that deletion until the modal is next refreshed; same family as risk 3. On phone-390 the habits grid's Days and delete tools still sit past the right edge of the band and need its internal sideways scroll to reach, as designed and previously recorded; their centres resolve correctly once scrolled. During the pass the service worker was stubbed out (a cache-first worker could serve a stale copy mid-iteration), and toasts were dismissed the way their own 5s timer would before measuring what sits under them.

Still true from earlier passes: the custom popovers at 1280x800 open inside the viewport, drive the underlying controls through their existing change handlers, and float unclipped over a scrolled board; with two habits and three weekly items the rail's scroll height is about 1400px against an 800px viewport, so the Momentum cards live below the fold (risk 9, accepted).

Known device-conditional behavior: layout branches at `window.innerWidth<900` in several functions (`windowDays`, `renderNav`, `goto-day`, and the tab-drop midpoint axis); hover styles are gated behind `@media (hover:hover)`; keyboard-driven resizes are ignored by design (width-only re-render). Tab reorder is pointer-only in practice: no mobile browser raises HTML5 drag events from touch, so on the coarse profiles the drag never starts and a touch on the header simply scrolls, exactly as it does on a card. That reachability gap is deliberate and recorded as risk 12, not silent.

**Nothing in this project has ever been verified on a physical iOS device.** The "iOS bug" turned out to be width-dependent, so the fix is believed device-independent, but Safari-specific behaviors remain unexercised: the `beforeunload`/`visibilitychange` commit path under Safari's aggressive tab freezing, `navigator.onLine` accuracy, date-input UX (`jumpDate`, `pickdate`), clipboard fallbacks in the sync modal, and PWA cache adoption timing after a `CACHE` bump (users must fully close the app; nothing in-app prompts them). The 60s `rollIfNewDay` timer does not run while iOS suspends the page; foreground events cover it, which is accepted.

## 8. Risk list, ranked

Risks 1, 3 and 9 of the revision before last are fixed, as is risk 4 (title vs tick) of the last one. This is the list as it now stands.

1. **An old client still strips newer keys during the window before every device updates.** The pass-through fix only helps clients running it. A device on a cached build older than `v19` reconstructs from its own whitelist and will drop `pos` (degrading merges gracefully back to the old combined behaviour) and `bin`. Exposure is bounded: the stripped key goes from the cloud copy, but the first updated client to sync restores it from its own local copy, so permanent loss needs the cloud to be the only holder, e.g. a fresh install that pulls before it has ever had a copy of its own. The manual cache-bump ritual decides how long the window lasts. `notes` is the newest key in this window: clients since `v19` carry it through the unknown-key pass-through even before they understand it (whole-array, content-tiebreak, converging), while anything older strips it from its uploads with the bounded exposure above. The note `pinned` flag (new in `v28`) is worse off than a top-level key, and this is the one genuinely new risk of the Notes rework: it is a per-item FIELD, so `carryUnknown` cannot protect it; a client older than `v28` rebuilds every note field-by-field in `rebuild()` and silently drops the flag on its first merge, unpinning everything. The exposure is cosmetic and self-healing (note text, titles and order are untouched, and re-pinning on an updated client re-asserts the flag on the pos axis), but until every device is on `v28` a pin can quietly vanish, and nothing records that it did. Same manual cache-bump window as always.
2. **Clock skew** flips every last-write-wins decision, now on two axes rather than one; there is no server-time anchor at all.
3. **`ui.skipBin`/`ui.binNote` debounce race** can misfile conversions into the bin or attribute a moved tab's annotation to the wrong commit; rare, silent, untested.
4. **Concurrent PUT race** leaves the cloud transiently missing one device's changes with no version check; converges only if the losing device syncs again.
5. **Drag and drop is only part-tested.** Tab reorder and plain card drops now have wiring coverage (synthetic events in jsdom, real constructed `DragEvent`s in Chrome, and since the polish commit the cues, the FLIP and the dragover short-circuit are pinned in both harnesses), so the shrinking uncovered remainder is the riskiest part: subtask re-parenting by drag and the two subtask-conversion branches with their `ui.skipBin` marks, which sit directly on the merge's most subtle contract (id survival vs conversion); a regression there corrupts sync state, not just UI. The browser's own pointer-drag loop also remains beyond every harness here.
6. **The 79-case click handler's return/break convention**: the next case added with the wrong exit either double-renders or never saves, and only manual testing would notice the latter. (`note-pin` is the newest case and uses `break`, riding the shared save-and-render tail.)
7. **A new field on an item must be classified twice** (Section 4): once into `sigC`/`sigD`/`sigP`, once into `CONTENTF`/`DONEF`/`POSF`. Nothing enforces the pairing, and getting it wrong loses edits silently.
8. **The picker layer intercepts input at capture phase** (Section 4): a future global keyboard feature that misses the `pop` check, or a click behaviour added to one of the three anchor controls, fails silently and only on desktop. Low likelihood, but the failure would look exactly like the two blank-button bugs: present in code, absent in behaviour.
9. **The rail no longer fits an 800px-tall desktop viewport.** True north, habits, the weekly list, four metric cards and the foot total ~1400px, so the metrics live below the fold and the rail scrolls. The empty-panel collapse trims that for anyone not using True north, Habits or This week, since each unused panel is one header bar; a rail with all three in use is unchanged. Accepted for now: the interactive bands sit first and the metrics are a readout. If it grates, the candidates are collapsing the Momentum block the way habits collapse, or folding Streak and Month into one card; both are decisions for the owner, not a refactor to smuggle in.
10. **`habits.marks` and `week.hist` only ever grow.** Every week's cells and archives stay forever (deliberately: history for review and future streaks), untick markers are kept as negative cells so they can outrank older ticks on late-syncing devices, and a deleted habit's marks are kept so a Restore recovers its whole record. The weekly sweep's archive week is also approximate for a device offline across several Mondays: everything files under the last week it saw. All of that is the same never-prune stance `state.days` takes, and it feeds the same `stateSig` cost noted in Section 4. A pruning pass, if one is ever wanted, must respect the 45 day tombstone horizon or an offline device resurrects old cells.
11. **The merge still has two data-loss classes, not one.** Same-field concurrent edits lose one side (Section 3, item 1): two devices renaming the same task, ticking it differently, moving it to different places, or, since this commit, editing the same note body, where the later `dn` takes the whole body and the older rewrite is gone without record or bin entry; unavoidable without a merge UI. The note body is now the costliest member of this class, paragraphs rather than a title, and it is NOT solved, only split so a title edit and a body edit compose; it is pinned by a test (the losing text asserted absent from the whole merged state) so it can only ever change deliberately. And subtask work loses to a concurrent parent delete (Section 3, item 4): a step ticked or added under a task another device deleted vanishes with no bin entry. The first is inherent; the second is a chosen rule ("never orphan a step") that could instead have revived the parent. Both directions are now pinned by tests, so the rule can no longer change silently, only deliberately.
12. **Tab reorder is unreachable by touch.** The reorder is a drag on the tab header, and no mobile browser raises HTML5 drag events from touch, so on phones and tablets the tabs can only be reordered from a pointer device; the order still syncs over once set. Card drag has always had this gap, but cards carry button equivalents in their action bar and tabs carry none, so the gap is real rather than cosmetic. Deliberately shipped this way and said out loud rather than patched: the smallest fix, if the owner wants it, is a pair of left/right minis in each tab header behind the same delegated-switch pattern the card's reorder arrows use, one new `case`, no new drag surface. The polish commit re-pinned the gap as a test (a real touch drag across a header is asserted inert on all three coarse profiles) and costed the minis for the owner, who has not yet decided; they are deliberately not in that commit.
