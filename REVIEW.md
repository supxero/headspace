## 0. The theme layer (new)

- **Mechanism.** `:root` declares the full palette as custom properties; `:root[data-theme="mono"]` re-declares the same set. No rule in the sheet hardcodes a colour: every fill, tint, border, shadow, gradient, scrim and label face reads a variable. Switching is ONE attribute write on `<html>`, so it applies in the same frame with no reload; a four-line head script applies the stored theme before the stylesheet exists, so a reload cannot flash the other theme. The running app's half (`themeGet`/`themeSet`/`themeApply`, the modal, the two click cases) sits in its own script section; both click cases `return`, never `break`, because the choice must never touch `save()` or the render/sync path.
- **What routing the sheet surfaced.** The theme work forced every hardcoded colour through variables; the sweep found and converted: the body's three radial washes and the dot-grid texture; the rail's powder gradient; the tray's four-layer sheen-and-glow composite (border, background, shadow, each now a variable held whole); ~60 `rgba(36,58,94,…)` navy tints, split by ROLE into `--ink-rgb` (fills, hover washes, borders) and `--shd-rgb` (box-shadows only), because a dark theme wants light washes but black shadows; denim, teal, pearl and cloud tints (`--denim-rgb`, `--teal-rgb`, `--pearl-rgb`, `--cloud-rgb`); the modal scrim; the progress ring's hardcoded SVG track stroke and its three gradient stop colours (now CSS-driven via `.rt` and `#rg stop:nth-of-type(n)`); the board-nav hint `#A9C4DB` and off-board note `#8FB6D8` (now `--oncanvas`, `--ocean`); the zone action-button inks `#2F4156/#3F6488/#3C6A8E` (now `--must-t/--should-t/--extra-t`); the primary buttons' pearl sheen layers (now `--sheen`/`--sheen2`, `none` in mono so the layered background collapses flat); and the date input's `color-scheme` (now `--oscheme`). Two JS-side colour sets were deliberately NOT converted: `NOTE_HL`/`NOTE_HL_RGB`, which are serialization tokens the sanitizer normalises into class names (the PAINTED highlight colours come from `--panel`/`--ocean`/`--tasktile` and theme correctly), and the inline `color-scheme:dark` on the per-task date field, which is identical in both themes.
- **Role splits the blue theme hid.** Four variables were doing two jobs and split, with the blue value duplicated so Cloud blue stays pixel-identical: `--canvas` (the board ground, was `--denim`), `--today` (today's marker, was `--teal`), `--okdot` (the sync all-well dot, was `--done`), and `--onpri` (ink on the primary/completion fills, was `--on`). Without the splits, mono's red today-marker would have painted every teal chip red and its light inverted toast would have carried light text.
- **The mono palette, verified numerically.** Surfaces `#070708` (canvas) → `#161619` (rail) → `#212126` (columns, cards) → `#28282D` (task tiles) → `#313138` (pearl); ink `#E9E9EC`/`#ABABB3`/`#85858D`, strong ink `#ECECEF`, brightest value `#F6F6F7` (ink on red), deliberately short of `#ffffff` in every channel so the no-white sweep passes in both themes. The red is `#E8443C` and backs exactly four variables (widened deliberately by the four-additions commit, 2026-08-12): `--done` (completion: tick fills, the ring, "done" marks), `--today` (column ring, TODAY badge, calendar cell, strip, habit-day header, and since the four-additions commit the active nav item's accent bar and icon tint, which reuse the variable rather than adding one), `--grad` (the primary action) and `--north` (the True north statements, Section 11). Both audits' whitelists were widened to match in the same commit: the jsdom declaration whitelist gained `north`, and the live sweep in `tests/viewports.js` gained the `.navbtn.on` subtree and the held-statement text. Every body-text/surface pair holds WCAG 4.5:1+, every label/accent pair 3:1+, in BOTH themes, enforced three ways: computed from the declared values in `tests/test.js`, computed live from rendered elements in `tests/viewports.js`, and re-checked after every flow because every audit now runs under both themes.
- **Typography.** Silkscreen (Google Fonts, OFL) loads through the same `<link>` as the existing faces and leads two new stacks, `--fdx` and `--fbx`, which only numerals and short uppercase labels read (column headers, zone labels, badges, calendar numerals, the big stats, panel headers, day-of-week rows); body text keeps the sans in both themes. In Cloud blue the stacks equal the existing faces, so nothing changes; if Silkscreen fails to load, the sans chain behind it renders and the app stays fully legible.
- **What the platform allows.** The `theme-color` meta follows the active theme (head script on boot, `themeApply` on switch), so browser chrome tints correctly on both. The manifest's `theme_color`/`background_color` CANNOT follow: a manifest is one static file read at install time, so an installed app's splash screen stays cloud blue whichever theme the device chose. Accepted and documented rather than worked around.

State flow: every mutation goes `handler mutates state -> save() (400ms debounce) -> commit() -> stampChanges() diff -> localStorage -> pushSoon() (1800ms debounce) -> syncCycle()`. Rendering is full `innerHTML` rebuild of each region on every `render()`.

Grown unwieldy:

- The delegated click handler (`index.html:3408`) is ~340 lines and 80 `case`s with two exit conventions: `return` means the case handled its own save/render, `break` falls through to a shared `save(); render()`. Picking the wrong one is an easy, silent mistake, and the pre-switch block that closes the inline add field (added for the mobile trap fix) runs a deferred `save(); render()` in a `setTimeout(0)` that has to guess whether a rename just started by sniffing `document.activeElement.dataset.kind`. It works and is tested, but it is the most fragile control flow in the file. **Enter no longer enters it.** Enter used to synthesize a click on the row's Add button, which put every committed task through that deferred block; it now calls `addChain` (Section 9) from the keyboard handler directly, so the chain path is a plain `save(); render()` on the same turn and the `setTimeout(0)` block is reached only by an actual tap outside the row. That is one caller fewer on the file's most fragile path, not one more.
- `render()` re-renders everything on every action. Fine at current data sizes, but it is why focus/caret preservation needs manual bookkeeping (`ui.adding`, `ui.addText`); any future input element gets the same class of bug until someone remembers that. One concrete cost, observed during the four-profile input verification: while any inline rename is open (task, tab, habit, weekly item, and the rename `float-new` auto-opens), the first tap on any other control is spent on the rename's blur, whose commit re-renders the tree under the gesture before mouseup lands, so that tap does nothing and the user must tap again. Pre-existing, affects every rename path equally, and inherent to commit-on-blur plus full re-render; noted here rather than patched. The Notes editor was checked against exactly this and does NOT make it worse: its title and body are a real input and textarea that write state on every `input` event through the save debounce, nothing commits on blur and nothing re-renders on a keystroke, so the first tap out of the editor lands (pinned by a test). What it does inherit is the foreign-re-render case: a render arriving from elsewhere (sync adopt, the midnight check) rebuilds the fields, so `renderNotes` restores focus and caret by hand, the same bookkeeping `ui.adding` needed; since the Notes rework the search box is a third such field, restored the same way with its query (`ui.noteQ`, memory-only) and its caret. Typing in the search box re-renders nothing at all: it patches `#noteRows` in place, calls no `save()`, and so can never steal focus from the editor or reset a caret mid-word (pinned by tests in both suites). The rich-text commit hardened the caret restore rather than weakening it: the body is now a contenteditable div, where a caret is a (node, offset) pair into a DOM the render throws away, so `noteCaretGet`/`noteCaretSet` flatten both ends of the selection to absolute offsets from the start of the editable root and walk the rebuilt text nodes to find the same characters again; the rebuilt DOM renders the same body string, so the offsets land exactly, including inside formatted spans (pinned in jsdom and in Chrome). Since the Notes data-integrity commit a LINE BREAK COSTS ONE CHARACTER in that numbering (both directions read one `noteWalk`), because counting only text made a line start and the previous line end the same number and the restore always chose the earlier one, which is Section 5, "The caret dropped a line on every foreign render". No keystroke can be lost to the swap, because every keystroke is already in state before any render reads it. The tab-drag polish was checked against the same first-tap cost and moves it in neither direction: while any rename is open, the press that would begin a drag elsewhere is spent on the blur, whose commit re-render replaces the pressed header before the browser's drag threshold is met, so the drag needs a second press exactly as a tap needs a second tap. The polish adds no press-time listeners (dragstart and its open-rename guard are untouched), and the FLIP runs only on a completed drop, which cannot coincide with a pending blur since the blur resolves at the drag's initial press.

## 2. State shape

```
state = {
  ver: 2,
  days:   { "YYYY-MM-DD": { must:[Task], should:[Task], extra:[Task] } },
  carry:  [Task],                    // + .from label on carried tasks
  focus:  [{ id, title, done, doneAt, up }],   // True north statements; done+doneAt now mean "set aside" + "held until"
  floats: [{ id, name, tasks:[Task], up }],
  tomb:   { id: msTimestamp },       // deletions, kept 45d (TOMB_KEEP)
  bin:    { id: { k:'task'|'sub'|'float'|'focus'|'habit'|'wtask', at, body, loc?, pid?, pname?, moved?, purged? } },
  habits: { list:[{ id, name, days:[1..6], up, dn, pos }],   // Mon=1 .. Sat=6, no Sunday
            marks:{ "mondayISO": { habitId: { dow: +-msTimestamp } } } },
  week:   { list:[{ id, title, done, up, dn, pos }],         // flat, no tiers, no days
            hist:{ "mondayISO": [{ id, title, at }] } },     // weeks already closed
  notes:  [{ id, title, body, pinned?, pg?, folder?, up, dn, pos }],  // body: plain, or sanitized HTML once formatted; folder: a folders[] id, or absent for the loose list
  folders:[{ id, name, up, dn, pos }],               // one flat level of note groups; a folder owns no notes
  sticky: { text, at },                              // ONE shared scratch block; merged whole by `at`, not an item
  settings: { view, boardOffset, floatMode, activeFloat, calSel, calOffset,
              mRange, stripDay, lastRoll, showDone, habitsOpen, lastWeek, noteSel }
}
Task = { id, title, done, subtasks:[{id,title,done,up,dn,pos}], up, dn, pos, from? }
```

The theme is deliberately NOT in this shape: it is a per-device screen preference stored beside the planner under its own key (`agora_dayplanner_theme`, values `sky`/`mono`), like `agora_dayplanner_synckey` before it. Putting it in `settings` would have synced it (wrong: a phone's dark choice must not restyle the laptop) or demanded a `VIEWSET`-style exclusion plus a merge classification for zero benefit. Tests pin that a switch leaves the planner's stored bytes and `stateSig` untouched.

Every mergeable item carries **three** stamps, merged independently (Section 3):

| Stamp | Covers | Declared in |
|---|---|---|
| `up` | title, a tab's name, a note's title and page appearance (`pg`), or a habit's name and active days | `CONTENTF`, `sigC` |
| `dn` | `done`, a focus item's `doneAt`; for a habit no fields, only the moment its marks last changed; for a note the entire `body` | `DONEF`, `sigD` |
| `pos` | location, order in its list (tabs, notes and folders included), a task's `from` label, a note's `pinned` flag and its `folder` assignment | `POSF`, `sigP` |

Habit ticks are the exception to items-carry-their-fields: they live outside the item in `habits.marks`, one cell per habit, week and day, holding a timestamp that is positive for ticked and negative for unticked. `mergeMarks()` unions cells and resolves a contested cell by larger absolute value, so a Monday tick on one device and a Wednesday tick on another can never conflict, which is the property the item's single `dn` stamp could not give. The habit's `dn` still moves when its marks change (`sigD` hashes them via `marksSigFor`), carrying no fields; it exists only so ticking a habit asserts it should exist against a concurrent delete, the same revival rule tasks have.

**The focus kind was reworked into the True north panel (2026-08-10) without touching its stored shape.** The user-facing name, the tick, the "open" count and the Completed section are gone; what remains is a statement panel whose archive gesture is "set aside". Set aside writes the very same `done`/`doneAt` fields the tick wrote (`doneAt` renders as "held until"), so the `dn` axis, `DONEF.focus`, `sigD`, the merge fixtures and every saved planner carry over with zero migration: an old ticked item IS a set-aside statement and files under the archive with its date. The archive itself is option (b) of an owner decision and is flagged reversible in `renderFocus`; reversing to no-archive means deleting the aside branch of `frow`, the Set aside section and three handler cases, with no data change. The panel is pinned open while it holds a current statement: the header then renders no chevron and carries no toggle action, and since no collapse flag for it is persisted anywhere (peek is memory-only), a planner holding statements can never load collapsed. Only the empty panel (set-aside statements do not count) collapses to its header bar, which reads "not set" rather than a count. Internal names (`state.focus`, the `focus-*` actions, bin kind `focus`, `settings.showDone`) deliberately keep the old word; the only place a user can meet it is the export file's `focus` key, which is the state key that must not change.

A note has no tick, so its `dn` axis carries the body instead (`DONEF.note=['body']`, `sigD` hashes the body): a title edit on one device and a body edit on another then compose instead of one discarding the other. What this does NOT solve, and nothing short of a merge UI or CRDT text would: two devices editing the same BODY resolve by later `dn` wins, whole body, and the older rewrite is silently discarded with no record and no bin entry. That is the same same-field class every item has (Section 3, item 1), but the payload is a body of text rather than a title, so it is called out separately in risk 11 and pinned by a test so it can only change deliberately. Anyone reasoning "dn means done" will misread notes; after this commit the axis really means "the second independently merged channel".

**A note's `pinned` flag rides the pos axis (new with the Notes rework, 2026-08-10).** Pinning says where the note sits (the top of the list), not what it says or what is written in it, so it is classified into `POSF.note` and hashed by `sigP`: a pin toggle bumps only the position stamp, composes with a concurrent title edit (up) and a concurrent body edit (dn), and, exactly like a move, cannot revive a note deleted elsewhere, since tombstones are compared against `up` and `dn` only. It deliberately does NOT touch how a body merges, which was the constraint. The flag is stored as `pinned:true` or absent, never `false`, so exports and old planners stay clean; `flatten` normalises it and `rebuild` writes it back only when set. The notes LIST on screen is a display sort, `noteOrder()`: pinned first, then by `max(up,dn)` (last edit; position moves do not count), ties in stored-array order. The stored array is never reordered by browsing, searching or the sort itself, so reading the list churns no stamps; only creation (`unshift`), deletion and restore still move array positions, exactly as before.

**The body can now hold light formatting, and the storage choice is the load-bearing decision (rich-text commit, 2026-08-10).** The body stays ONE opaque string on the dn axis. The serializer (`noteSerialize`) writes plain text whenever a note contains no real formatting, byte-identical to what the plain era stored, and flips to a sanitized HTML subset only when formatting actually exists: `div`/`br` for lines, `b`/`i`/`u`/`s`, `ul`/`ol`/`li` plus `ul.dash`, and `span` carrying exactly one of five classes (three palette highlights, two sizes). One sanitizer (`noteScrubbed`) is the whole contract: it runs on every keystroke's serialization and again on every render, strips every attribute, maps execCommand's `font` tags and style spans into the classes, and unwraps or drops everything else. Whether a body is rich is sniffed, not flagged: a body starting with `<div`/`<ul`/`<ol` (only the serializer writes those) renders as markup, anything else renders escaped, so a legacy plain note that literally contains `"<b>"` stays literal text. Migration is therefore lazy and lossless: nothing rewrites stored bodies at load (a load-time rewrite would restamp `dn` and out-vote real edits made elsewhere); a plain body converts to editor DOM at render and back to the identical plain string on the first input. Search, previews, labels and the word count read `noteText()`, the markup-blind text, so a phrase crossing a tag boundary still matches and tag names can never produce phantom hits. The bin, export and import all carry the body as the string it is.

**A note's `pg` (page appearance: `'ruled'`, `'dot'`, or absent for blank) rides the content axis** beside the title, the way a habit's schedule rides beside its name: it is authored presentation, not placement, and it must never sit on dn, where a page flip on one device would take the whole body with it against an edit made elsewhere. Cost accepted and pinned by a test: a page flip and a title rename made concurrently on two devices resolve by later-up-wins-both, the same small-payload rule habits already accept; a page flip beside a concurrent body edit composes. Stored as the value or absent, never a default string.

**A note's `folder` rides the pos axis beside `pinned` (four-additions commit, 2026-08-12), and a folder is a merge kind of its own.** Filing a note is saying where it sits, so `folder` is in `POSF.note` and hashed by `sigP`: a move composes with a concurrent title edit (up) and body edit (dn), two concurrent moves resolve by later-pos-wins the WHOLE placement (folder, order and pin together, one winner), and a move cannot revive a note deleted elsewhere. The `folder` kind itself is the plainest one in the table: name on content, nothing on dn (like a float tab), order on pos; folders merge item by item, tomb and bin included. The load-bearing asymmetry: moving a note INTO a folder stamps the NOTE, never the folder, so it does not defend the folder against a concurrent delete; `rebuild()` drops any note reference to a folder that was not kept and the note lands back in the loose list, notes never dying with their folder by construction (`renderNotes` tolerates a dead reference the same way mid-merge). Deleting a folder in the UI moves its notes out first (the confirm modal, same contract as tab delete) and bins only the folder, with the moved ids annotated so Restore gathers the still-loose ones back in.

**The sticky block is deliberately NOT an item.** One text, one stamp (`at`), written together at every keystroke in the input handler, so the unstamped-debounce window that once cost a note body its merge (Section 5) cannot exist for it: whenever the text is newer, so is its stamp. It merges whole in `rebuild()` (later `at` wins, ties break by content so both sides converge, a missing side never wins, so a pre-sticky planner cannot blank it) and is hashed explicitly in `stateSig` (it is a known key, so the unknown-key sweep never sees it). The exposure is the same one a note body has and is stated rather than solved: two devices editing it concurrently keep the later text whole and the earlier rewrite is silently gone, no record, no bin entry (risk 11).

Anything written before a split has only the older stamps; `posOf()`/`dnOf()` fall back to `up`, and `stampLegacy()` backfills both at load, so a split becomes fully active after one save.

Synced vs local:

- **Merged item-by-item:** everything under `days`, `carry`, `focus`, `floats` (tasks, subtasks, tabs), `habits.list`, `week.list`, `notes`, plus `tomb` and `bin`; `habits.marks` merges cell-by-cell as above, `week.hist` by union (`mergeHist`, newer `at` wins a shared id). Weekly items are the plainest kind of all: title on content, `done` on its own dn axis, order on pos, exactly the focus-item shape. Tab order needed no new field at all: it is the floats array order, already stamped on `pos`, so the drag reorder rides the same axis task order always has. `emptyPlanner()` now counts notes as content, so a notes-only device is not silently overwritten by `connectKey`.
- **Device-local under merge:** the entire `settings` object. `rebuild()` (`index.html:1355`) takes only `mine.settings`. `VIEWSET` (`index.html:1486`) is used only by the manual-Pull path (`applyCloud`) to keep local view state while importing the rest of the remote settings. So merge and manual Pull treat settings differently; that asymmetry is deliberate but undocumented outside this file.
- **localStorage, never in the cloud blob:** the sync key (`agora_dayplanner_synckey`), agreement stamp (`agora_dayplanner_syncstamp`), pre-pull backup (`agora_dayplanner_v1_backup`).

**Unknown top-level keys now pass through (fixed, was the headline risk).** `rebuild()` still reconstructs the keys it understands, declared in `MERGED_KEYS`, but it ends with `carryUnknown(out, mine, theirs)`, which copies through every top-level key neither side's merge logic knows about. A key added to `state` in future therefore survives a merge instead of being silently dropped. It gets no last-write-wins (there are no stamps for it): whichever side has it wins, and if both differ the smaller JSON wins, which is arbitrary but identical on both devices, so they still converge. `stateSig()` hashes unknown keys too, so a change to one still triggers a push. A test asserts `MERGED_KEYS` still matches `Object.keys(fresh())`, so adding a key to the canonical shape fails the suite until someone decides whether it needs real merge semantics or the generic pass-through is fine.

## 3. Sync and merge

Mechanics: one Supabase row per sync key, whole-state JSON in `data`, publishable API key embedded in the page. `syncCycle()` (`index.html:1681`) runs on boot, focus/visibility, reconnect, a 25s poll, and 1.8s after any edit. It does GET, **`flushSave()`**, `mergeStates(local, cloud)`, adopts the merge if it changed anything, and PUTs if the cloud is missing anything, comparing via `stateSig`. The flush is load-bearing and sits AFTER the round trip, not before it: stamps only move at commit, so any edit still inside the 400ms debounce would otherwise reach the merge carrying the previous commit's stamps and be weighed as though it had happened at that older moment (Section 5, "A keystroke merged away"). Every actor that reads, re-stamps or replaces the whole tree now flushes first: `syncCycle`, `applyCloud` (so the Undo backup holds what was being typed), `pushNow`, and `rollIfNewDay`, which had the only such guard before this commit. The Push/Pull buttons are raw overwrites in both directions (documented in the sync modal); Pull backs up to `agora_dayplanner_v1_backup` and offers toast-undo.

Merge rules: union by id. Per item, **title, tick and position are resolved separately**: the side with the newer `up` supplies the title, the newer `dn` supplies the tick, the newer `pos` supplies location/order/`from`, and `pickNewer()` splices the three together. Equal stamps break by JSON comparison of just the fields under that stamp, so both devices agree. That tie-break is a convergence device, not a merge rule: it is right only when the two sides genuinely happened at the same recorded moment, and it is fed garbage by any state that reaches it under-stamped, which is what the flush above now prevents. A tombstone kills anything whose `up` **and** `dn` are both older than the deletion: editing or ticking asserts the item exists, moving it does not. `stampChanges()` assigns all three by diffing a structured signature (`{c,d,p}`, no separator to collide with user text) at commit time, so every mutation path is covered without instrumentation. Habit rows ride the same axes, with the schedule (`days`) as content beside the name; their ticks merge cell-by-cell instead (Section 2). The weekly list turns at Monday 00:00 through `weekSweep()`, gated per device by `settings.lastWeek` the way the daily roll is gated by `lastRoll`: ticked items graduate into `week.hist` under the week that closed and leave the tree, so the normal diff tombs them (a stale device's ticked copy cannot bring them back) while `ui.skipBin` keeps them out of the bin, since finishing a week is not a deletion. Unticked items simply stay, which is the carry. A device off for several weeks archives its finished items under the last week it saw, an accepted approximation. Subtasks are not listed in their parent's signature, so adding a step does not restamp the task it belongs to. Bin entries follow their tombstones; purge markers are terminal.

Cases resolved by an arbitrary rule or still able to lose data:

1. **Two edits to the same field: later stamp wins, the loser is silently discarded.** Now genuinely narrow. Rename versus tick is fixed (`dn` is its own axis), as is either versus a move. What remains within edit-versus-edit is same-field-versus-same-field: two devices **renaming the same task** to different text, two **ticking it differently** (an untick after a tick, and the later one wins), two **moving it to different places**, or, new with the Notes view, two devices **editing the same note body**, where the later `dn` takes the whole body and the older rewrite goes without record or bin entry. The note case is the costliest instance of this class, since the payload is paragraphs rather than a title; a title edit against a body edit composes fine (separate axes), body against body has one loser. One side loses, with no record and no merge UI. Renaming two *different* tasks, or renaming one while ticking or moving it, all survive intact. Delete conflicts have losers of their own, item 4.
2. **Reorder vs content edit, and rename vs tick: both fixed.** The signature was split three ways (`sigC`/`sigD`/`sigP`) with a stamp each. A reorder bumps only `pos`, a rename only `up`, a tick only `dn`, so none can discard another, in any direction, and all three compose on one task at once. Tested fourteen ways, including every mirror case and convergence. Reverting either split fails six assertions each.
3. **Move vs rename: fixed** by the same split. The task lands in the newly moved-to place carrying the newly typed text.
4. **Edit or tick after delete resurrects** (deliberate, tested). Ambiguous case: the stamps and the tomb are compared across devices with unsynchronized clocks. **A reorder or a move no longer resurrects a deleted item**, since the tombstone is compared against `up` and `dn` only; editing or ticking asserts the item should exist, shuffling it does not, and pinning a note is shuffling, not editing (pinned by a test in both merge directions). **Revival is strictly per item: work on a subtask does not defend its deleted parent.** Delete a task on one device while another ticks one of its steps, or adds a brand new one, and the steps die with the parent, silently, with no bin entry anywhere in the merged state; `rebuild()` drops any surviving step whose parent was not kept ("never orphan a step", `index.html:1374`), even a step whose own `dn` beat the tombstone. Conversely a parent revived by its own rename comes back with zero steps, since its old steps were tombed individually and nothing re-asserted them. Pinned by tests in both merge directions, including the no-bin-entry fact and the parent-rename contrast.
5. **Clock skew skews everything.** All conflict resolution is `Date.now()` comparison. A device minutes fast wins conflicts it should lose. Nothing detects or compensates.
6. **No optimistic concurrency on the row.** Two devices can GET the same cloud state, merge, and PUT; the second PUT overwrites the first. Nothing is destroyed locally, and the next cycle re-merges and re-pushes, but the cloud can be transiently missing one device's changes, and a device that stops syncing right after losing that race leaves the cloud stale.
7. **Expiry horizons:** bin bodies 30d, tombstones 45d. A device offline more than 45 days resurrects its stale copy of deleted items as "edits after delete".
8. **`emptyPlanner()` ignores `tomb` and `bin`,** so a device whose planner is all-deleted counts as empty; `connectKey` will then adopt the cloud wholesale and discard the local bin bodies.
9. **Restore vs permanent-delete race:** restore wins the item, purge only strips the stored body. Deterministic, but chosen, not derived.
10. **Carry-over tray, observed in Chrome 2026-08-10.** An automatic merge cannot empty or hide the tray: verified against a cloud copy predating rollover and against one with `carry:[]`, the locally carried items win both times. **Exception A is now fixed** by the content/position split: a task rolled into the tray here and renamed on another device after midnight keeps its place in the tray, picks up the rename, and keeps its "Prio 0 · Sun" origin label, because `from` is positional and the rename only moves the content stamp. Pinned by a test. A manual **Pull** still empties the tray by design, restoring the tasks to their day columns, with Undo in the toast.
11. **The once-per-day gate is now visible rather than silent.** `rollIfNewDay` still returns immediately when `settings.lastRoll === today()`, so anything landing on a past day after today's sweep is not swept automatically, which is deliberate: continuous sweeping would fight a user who back-dates a task on purpose. What changed is that the board nav now renders a button reading "N waiting on past days" whenever unfinished tasks sit on past days (`pastOpenCount()`), and pressing it runs the sweep on demand, stamped now rather than at midnight since it is a deliberate act. The gate's behaviour is asserted by a test driven through `rollIfNewDay`, not `rollover`, so it cannot change silently.
12. Manual Push/Pull remain whole-blob overwrites; a habitual Push from a stale device wipes cloud-side items until another device's next merge re-uploads whatever it still holds (items deleted only in the cloud copy come back; items only in the cloud copy are gone for good unless another device holds them).

## 4. Known weak points

- **`ui.skipBin` / `ui.binNote` are side-channels** between three click-handler cases (`spop`, the two drag-conversion branches, `float-del-move`) and the next `stampChanges` run, carried in mutable `ui` fields and cleared unconditionally per commit. If an unrelated commit fires inside the 400ms save debounce (e.g. a sync `adopt()`), the flags are consumed by the wrong commit: worst case a popped-out subtask also shows up in the bin as a "deleted" step. Low probability, unhandled, untested. (`ui.drag`'s new `over`/`rect`/`side` cache is not in this class: it lives and dies inside one drag gesture, is cleared by dragend, and never reaches a commit or the serialized state.)
- **`prevSnap`** (the deep copy backing `binCapture`) must be refreshed by every path that swaps state; today `load()` and `commit()` do it and `adopt()` gets it transitively via commit. A future state-swapping path that forgets will produce bin entries with wrong or missing bodies, silently.
- **Three stamps per item now, and all three must be maintained.** `stampChanges` writes `up`, `dn` and `pos` from a three-part signature; a future field added to an item must be classified into `CONTENTF`/`DONEF`/`POSF` (used by `pickNewer` for tie-breaks) *and* into `sigC`/`sigD`/`sigP` (used to decide which stamp moves). Miss the signature and the field never triggers a stamp, so edits to it silently lose merges. Nothing enforces the pairing; a test that round-trips every field through a merge would. The habit kind adds a twist: its `sigD` reads the item's marks through `eachItem`'s meta (`marksSigFor`), so the dn stamp depends on state outside the item itself; anyone adding a second such out-of-item signal must remember to thread it through the meta the same way. The note kind bends the axes the other way: `dn` carries no tick but the whole body, and since the True north rework the focus kind's `dn` means "set aside", not completion, so the axis names no longer describe their cargo for every kind; the tables in `CONTENTF`/`DONEF`/`POSF` are the truth, not the names. The note's `pinned` flag is the newest worked example of the pairing done right: it sits in `POSF.note` AND in `sigP('note')`, so a pin toggle both restamps and wins ties on exactly one axis; miss either half and pins would silently lose merges, which is precisely the trap this bullet warns about.
- **The custom picker layer has two contracts nothing enforces.** On hover:hover devices a popover replaces the native date popup and the `#qd` dropdown (the natives are unstylable and OS blue); the native inputs and all their handlers stay untouched, the popover writes `value` and fires the same bubbling `change`. Contract one: while a popover is open, a capture-phase keydown handler owns Enter, Space, arrows, Escape and Tab and stops propagation, so a future global key feature must check the layer's `pop` state or it will never see those keys. Contract two: a capture-phase click handler swallows clicks on the three anchor controls (the `pickdate` input carries a `data-action`, and its raw click used to fall through the delegated switch into a stray `save()+render()` that closed the popover through the board scroll reset), so giving those anchors real click behaviour in the delegated switch will silently not work on desktop. Both contracts are pinned by tests. A third choice is deliberate: after a mouse pick the date input is left unfocused, since Chrome paints the focused segment highlight in OS blue and no CSS reaches it; keyboard flows do restore focus, and that highlight is then the focus indicator.
- **Two-field board position** (`boardOffset` for wide, `stripDay` for narrow) still exists; `shiftBoard()`/`showDay()` keep them in step at the five current call sites, but `windowDays()` (`index.html:2356`) still branches on `window.innerWidth<900`, so any new navigation control must go through the helpers or it will regress exactly like Prev/Next did on iOS.
- **`paintBin()` is called from `commit()`**: a DOM write inside the persistence layer, because renders don't run on commit. Works, but it is the only place data-layer code touches the DOM besides the save badge, and it will confuse anyone refactoring commit.
- **Copy rules are enforced by habit, not tooling.** No-white / no-emoji / no-em-dash checks live in `visual.py`, which cannot currently run (no Python). Reviews have relied on grep.
- **The cache-bump ritual** (`sw.js` CACHE constant) is manual and unenforced; CLAUDE.md calls it the most common mistake, and nothing in the test suite checks that the constant changed alongside `index.html`.
- **`state.days` is never pruned.** History is the data model (metrics, streak), so this is by design, but `syncCycle` runs `flatten`+`stateSig` up to three times per cycle, every 25 seconds, over everything ever created. Years of data on a low-end phone will make the poll visibly expensive.
- **The unstamped window is a hazard class, not a footnote.** Between a mutation and its commit, `state` holds data that is newer than its own stamps, and everything that resolves conflicts reads stamps. This shipped as a data-loss bug once already (Section 5, "A keystroke merged away"), and the guard is `flushSave()` at every entry point that reads, re-stamps or replaces the tree. The list is short and must stay complete: `syncCycle`, `applyCloud`, `pushNow`, `rollIfNewDay`. Nothing enforces it. Anything future that merges, exports for comparison, or backdates a commit with `commit(when)` belongs on it, and the tell that it was missed is silent: the older copy simply wins. Worth knowing that `rollIfNewDay` had the guard from the day it was written, with the comment "pending edits keep their own moment", and the sync path never got it; a fix that lives in one caller instead of in the thing being protected is exactly the shape that leaves a second caller behind.
- **Quota/private-mode handling is a toast** ("not saving") plus in-memory operation; `sync.pending` is memory-only, so a kill while offline loses nothing (merge recovers) but a kill mid-typing loses the debounce window (up to 400ms of edits). The Notes editor widens that window: it calls `save()` on every keystroke and each call resets the 400ms timer, so typing that never pauses defers the commit for as long as the typing runs. Any pause, blur, tab switch or close flushes it (`visibilitychange`/`beforeunload` commit), so the exposure is a hard kill mid-sentence, losing back to the last 400ms pause rather than a bounded 400ms. The Notes rework changes none of this: title and body keystrokes ride the same per-input `save()` they always did, the meta line and the list row are patched in place without touching the save path, and the search box calls no `save()` at all, since the query is `ui`-only and nothing about searching persists. Rich text changes none of it either: a toolbar command applies, serializes and calls the same debounced `save()` a keystroke does, with no render, so the typing-defers-the-commit shape is exactly as recorded above; what each keystroke now costs is one parse of the editor's HTML through the sanitizer, trivial at note sizes but linear in note length, which is worth remembering if anyone ever pastes a book.
- **The rich-text surface adds three contracts nothing enforces globally.** One: `noteScrubbed` is the only gate between contenteditable's arbitrary DOM and the stored body; every path that writes a body must pass through `noteSerialize` (input, toolbar commands) and every path that renders one must pass through `noteBodyHtml` (render), or unsanitized markup reaches `innerHTML`. Both call sites exist today and tests pin the sanitizer's output, but a future path added around it fails silently. Two: the toolbar preventDefaults on `mousedown` (a document-level listener) so pressing a control never blurs the editor or collapses the selection the command is for; since the step-button follow-up (Section 9.5) it is scoped to the whole strip rather than to `#noteTools .ntb`, because Chrome does not dispatch mousedown from a disabled button and a press on a dead Undo would otherwise have blurred the editor. The page select is the deliberate exception, its dropdown needs the default. The trap that remains: a future control added to the toolbar that needs its own default behaviour must be excluded by hand the way `#notePage` is, or it will not respond to a press at all. Three: a `selectionchange` listener repaints toolbar state whenever the caret moves inside the editor; it is gated to the notes view and the focused editor, but it joins the picker layer's capture-phase keydown in the small set of document-level listeners a future feature must know exist. Paste is deliberately plain: the clipboard's `text/plain` is inserted via `insertText`, so outside formatting never enters, at the accepted cost that formatting is lost even when pasting from another Headspace note.
- **The Notes editor now owns four keys, and ownership is invisible from anywhere else.** `#noteBody` claims Ctrl/Cmd+Z, Ctrl+Y, Ctrl/Cmd+Shift+Z and, conditionally, the space bar, in a block at the TOP of the app-wide `keydown` handler (`index.html:3893`) that runs before the Enter and Escape branches. Nothing signals that from the editor's markup or from the toolbar, so a future global shortcut on any of those chords will be silently swallowed while the caret is in a note, and a future feature that wants the space bar in the editor has to know this block exists. The dash branch is written to fail open (both rules return false and the space falls through to the browser unless the caret is in exactly the right shape), which is the safe direction, but the undo branch is unconditional: inside `#noteBody` those three chords never reach anything else.
- **`ui.noteHist` is the second piece of editor state that lives outside `state`,** after `ui.noteQ`. That is correct (an undo history must never sync, and a merge must never carry one device's steps to another), but it means the editor's behaviour now depends on a mutable `ui` field whose ONLY invalidation rule lives in `renderNotes`. Any future path that writes `notes[i].body` and does not render, or that renders the notes view without going through `renderNotes`, breaks the staleness check that keeps undo out of the merge's way. There is exactly one such rule and it is load-bearing.
- **The live-patch/undo conflict is now permanent, not resolved.** The reason the native stack was unusable (a `textContent` write outside the editable on every `input`) is still there and still deliberate: it is what keeps the row label, the snippet and the word count honest mid-sentence. The app carries its own history around it rather than removing the cause. Anyone who later removes those patches will find the native stack quietly usable again and may not realise the hand-rolled one has become redundant; anyone who ADDS a similar patch elsewhere will find they cannot rely on native undo in that surface either.
- **Quick patches acknowledged as such:** the `setTimeout(0)` outside-tap logic in the click handler (Section 1); `binWhere`'s guards for malformed `loc` return vague labels rather than validating entries on write; `restoreBin` re-uses ids on restore (safe today because revival clears tombs, but it means id uniqueness across time is not an invariant anyone can rely on); and the import path stamps only `up` when it adopts a file, so an import asserts titles and schedules as the newest word but not ticks, and now not note bodies either, since those ride `dn`, nor pins, since those ride `pos`. A body edited on a live device after the export therefore survives an import of the older file, which is arguably the right outcome but is not what the comment beside the import promises.

## 5. Regressions and history

- **Mobile inline add trap** (fixed `b6f9c50`): root cause was the resize handler rebuilding the board when the soft keyboard opened. Actually fixed: resize now re-renders only on width change, typed text lives in `ui.addText`. Residual: a *real* width change (rotation) mid-typing still rebuilds; text survives, focus is restored, but the keyboard may flicker. The underlying innerHTML-rerender architecture that caused it is unchanged.
- **Devices overwriting each other** (fixed `33134a3`): whole-blob last-write-wins replaced by the per-item merge. Actually fixed and heavily tested; residual ambiguities listed in Section 3.
- **iOS Prev/Next dead** (fixed `68df415`): not iOS at all; `nav` wrote `boardOffset` while narrow layouts read `stripDay`. Fixed properly at the cause (`shiftBoard`/`showDay`), but the dual-field design that made it possible is still there (Section 4).
- **Carry-over tray vanished** (fixed `13b5551`): `rollover()` had only ever run at boot; auto-sync removed the daily restart that masked it. Actually fixed (`rollIfNewDay` on foreground + 60s timer, midnight-dated stamps, `lastRoll` made device-local). Residual: rolling happens only while the app is foregrounded, so the tray appears on next look, not at 00:00; that is an accepted platform limit, not a bug. **Re-verified end to end in headless Chrome on 2026-08-10, not just in jsdom**: seeded an unfinished task on yesterday with a stale `lastRoll`, and at both 390px and 1280px the tray rendered with the right items, kept the finished task on its day, showed correct origin labels ("Prio 0 · Sun"), placed every triage control in the viewport with `elementFromPoint` returning the control itself, and a real click on "Today" moved the task to today's Prio 0. The feature is genuinely working. Anyone reporting it "broken" has almost certainly hit the once-per-day gate (Section 3, item 11) rather than a defect.
- **Per-task date field dead on click** (fixed in the habits commit): tapping the mm/dd/yyyy field in a task's action bar did nothing, on a Free Floating tab and a day column alike, while every other control in the bar worked. Cause: the input carries `data-action="pickdate"`, so its raw click was funnelled into the delegated switch, matched no case, and fell through to the shared `save()+render()` tail; `renderBoard()` rebuilds `#board.innerHTML` unconditionally, so the input was destroyed in the same task that would have opened the native picker. The `tofloat` select had been given a bare `case 'tofloat': return` long ago, which is exactly why "file to" worked; `pickdate` now has the same case. `#jumpDate` was never affected: it carries no `data-action`, so the handler exits before the switch. On desktop pointer devices the custom picker layer had already masked the bug by swallowing the click; the fix repairs the native path phones actually use. Pinned by tests on both controls.
- **A highlight or size, once applied, could not be removed** (fixed in the verification commit; shipped broken in the rich-text commit, live for under a day as `v29`/`v30`): the remove path relied on the engine, and the engine's remove shapes vary. Clearing a size lays `font-size: medium` over `span.fz-*`, where `noteStyleCls` read the carried class as truth and re-asserted it; removing a highlight sometimes lays `background-color: transparent` on the span, but can also nest a fresh transparent span INSIDE it, leaving the class standing whatever the sanitizer does. Two-part fix: in the sanitizer, a style that names a channel is the engine's newest word and overrides the carried class (with nothing left, the body rightly collapses back to plain text); and highlight toggle-off no longer uses the engine at all, it finds the ancestor `span.hl-*` and unwraps it structurally, text unchanged, caret offsets preserved. Caught by the extended four-profile verification pass, the first to drive the toggle-off path, across two runs (the first fix survived the styled-span shape, the second run exposed the nested shape); pinned in jsdom as both engine shapes plus the structural unwrap. The pattern to note: every sanitizer defect so far has come from Chrome's editing engine reusing or nesting existing elements instead of writing the fresh spans the happy path assumes.
- **Tab delete control missing** (fixed `c21bff6`): never broke; it had shipped with an empty label since the initial commit and rendered at 10x4px. Fixed with a label and a test asserting visible text, plus the same fix applied when the tray's "Free Floating" button was found blank earlier. Two blank-button bugs from the same cause suggests scanning for empty interactive elements belongs in the visual suite; it is not there yet.

- **A keystroke merged away** (fixed 2026-08-12, the reported "typing then deleting occasionally reverts, as though an older version of the body came back"). Reproduced deterministically. A note's body rides the `dn` stamp, and `dn` only moves at commit; the editor calls `save()` on every keystroke and every call resets the 400ms debounce, so a typing burst leaves `state` holding a body newer than its own stamp. A sync cycle landing in that window (the 25s poll, or the `flushPush` 1.8s after the previous commit) compared the unstamped local body against the cloud's copy of the SAME `dn` and fell through to `pickSide`'s tie-break, which compares the two strings: `JSON.stringify(["hellox"]) > JSON.stringify(["hello"])`, because the next typed character outranks the closing quote for anything above `"`. So appending an ordinary character LOST, the cloud's older body was adopted, re-rendered under the caret and written to localStorage, while deleting a character (a shorter string sorts first) won and looked fine. That asymmetry is why it read as intermittent: the same act failed or passed on the character typed. Fixed at the cause, `syncCycle` now flushes the debounce after the GET and before the merge, so a body that is newer is also stamped newer and wins on merit; the tie-break is left exactly as it was, since changing it would break convergence. Pinned by nine assertions driving a real cycle against a fake cloud, both directions of the sort order, a genuinely newer remote body still landing, and a burst of type-and-delete with a full cycle after every keystroke.
- **The caret dropped a line on every foreign render** (fixed 2026-08-12, the reported "characters appearing where they were not typed"). `notePoint` counted only text characters, so a line break cost nothing and the start of a line and the end of the line before it were the SAME offset; `noteCaretSet` resolved that offset to the first text node that reached it, which is always the earlier one. Any foreign render with the caret at a line start therefore moved it up a line, and the next keystroke, and everything typed after it, went there. The 25s sync poll is a foreign render, so this fired on its own with no other device involved. Both directions now walk one shared function (`noteWalk`) that flattens the root the way `noteText` does, one character per `<br>` and one per block boundary, with a zero-length anchor recorded for the empty line a lone break holds open. The same rewrite fixed the neighbouring case: an offset past the end of a body that shrank under the caret (a losing merge, an Undo) used to resolve to the root's child list, where the next character is typed outside every line; it now clamps into the end of the last line. Verified in jsdom and by typing into real headless Chrome.
- **A nested block ate its line break** (fixed 2026-08-12, found while auditing the two above). `noteAsPlain` read only the editable root's own children and joined their text, so `<div>one<div>two</div></div>`, an ordinary Chrome shape after an Enter, serialized as `onetwo`: two lines silently became one on the very next keystroke, with no way back. It now walks recursively on the same "a block opens a line unless the line it would open is already empty" rule the caret counts by, which is the point: the serializer and the caret now disagree about nothing.
- **Not found: the reported "0000".** The second symptom, a string of four zeros appearing in a note that nobody typed, is NOT explained by any of the three fixes above and was not reproduced. What was ruled out, and how, is in Section 6 under "the 0000 report".

- **Undo had never worked in the Notes editor** (fixed 2026-08-12, this commit; broken since the editor shipped, never reported and never noticed by any test). Not a regression so much as a hole nobody had looked into, and it had three independent causes rather than one, all three now measured in Chrome and committed as checks (Section 9.2): the native stack died with the editor element on every foreign render, so the 25s sync poll wiped it about twice a minute unprompted; the live row/meta patches, a `textContent` write outside the editable on every keystroke, collapsed Chrome's typing coalescing to one character per press; and the two failure modes hid each other, since a history that only ever went back one character was rarely used long enough for anyone to notice it also kept vanishing. Fixed by carrying a bounded history over the body string rather than by removing either cause: the live patches are the feature that keeps the list row honest, and the rebuild-on-render architecture is the whole app.

Pattern worth naming: two of the first five were latent from day one and only surfaced when adjacent behavior changed. The suite now pins each one, but the class of bug (markup present, visually absent; feature keyed to a lifecycle that stopped happening) is what to watch for.

## 9. Input and interaction (new, 2026-08-12)

Four changes were asked for. Three shipped; the fourth is reported as not achievable, with the reason and the alternative, because shipping a half-working version of it would have been worse than shipping nothing.

### 9.1 Enter chains the next task

`addChain(k)` (`index.html:3399`) sits beside `closeAdd` and is called from ONE place, the keyboard handler's `d.enter==='add'` branch. It commits the field's text into the same destination key, then leaves `ui.adding` set to that same key with `ui.addText` cleared, and calls `save(); render()`. `render()`'s existing tail block re-focuses `.addin[data-k=…]` whenever it is not already focused, so the fresh field is focused inside the same turn. An empty commit is the way out: `addChain` sees no text, calls `closeAdd(false)` and closes. Escape is untouched, the Add BUTTON is untouched (it still commits and closes: the finger is already on it, and a second tap reopens the row), and the outside-tap path is untouched.

**How the mobile trap was kept out.** The original trap (Section 5) was the resize handler rebuilding the board when the soft keyboard opened, tearing out the live input. Two things keep the chain clear of it. First, `addChain` deliberately does NOT call `closeAdd` on the chaining path: `closeAdd` blurs the input, and a blur is what drops the on-screen keyboard, so blurring and re-focusing between tasks would make the keyboard fall and rise on every Enter. The old input is instead simply replaced by the render, and focus moves to its successor on the same turn, which every mobile browser reads as focus travelling between two fields rather than as leaving text entry. Second, nothing about the resize contract changed: `resize` still returns early unless `window.innerWidth` actually changed, and half-typed text still lives in `ui.addText` rather than only in the DOM. The residual is the same one the trap fix left behind and no worse: a REAL width change (rotation) mid-chain rebuilds the board; the text survives and focus is restored, but the keyboard may flicker.

Pinned on the coarse profiles specifically, at the shrunk keyboard-up height, by the `enter-chain` flow: four tasks typed one after another in order, the reopened field empty and focused and keyed to the same zone, exactly one field open at a time, no sideways overflow, the field still reachable inside the viewport with the keyboard up, half-typed text surviving the keyboard closing again, the same behaviour on a Free Floating tab, and both ways out (empty Enter, Escape) committing nothing.

**The quick-add box was left alone, and this is a proposal rather than a decision taken.** It is a `<textarea>` whose whole point is multi-line paste, so Enter commits and Shift+Enter is its newline. It never opens or closes, so there is no field to reopen: `case 'quickadd'` empties it in place and `renderQuick()` rebuilds only the `#qd` option list, never `#qi` itself, so focus and the caret survive the render untouched. Typing several tasks in a row from the top box therefore ALREADY works with no change at all, and both suites now pin that (`quick add: Enter empties the box in place`, `and keeps the caret in it`, `two in a row without reaching for the pointer`). The one thing it does not do is show you where the tasks went. If that is wanted, the honest change is a different one: keep the destination select from resetting attention, not add a chain.

### 9.2 Undo and redo in the Notes editor

**What was actually found, before anything was designed.** Three measurements in real headless Chrome, all of them now committed as checks in `tests/viewports.js` so they stay measurements rather than becoming folklore:

1. A bare `contenteditable` with no listeners undoes a typed run of three words in ONE Ctrl+Z. Chrome coalesces typing correctly.
2. Add one listener that writes `textContent` on an element OUTSIDE the editable on every `input`, and the same typing undoes ONE CHARACTER per press. That is exactly what the Notes input handler does: it patches the list row's label, the row's snippet and the meta line live so the word count and the untitled-note label stay honest mid-sentence. The feature that keeps the list truthful is the feature that shredded undo.
3. `renderNotes` rebuilds `#noteBody`, and a fresh element starts with an EMPTY native stack. Every foreign render therefore wiped undo silently, and the 25s sync poll is a foreign render, so on a synced device the history evaporated roughly twice a minute with nobody touching anything.

Any one of those is disqualifying; the third is fatal on its own. So the history is the app's: `ui.noteHist = {id, past[], future[], cur:{body,s,e}, at}`, snapshots of the body STRING with the caret as the same absolute text offset the caret restore already uses, so a step back lands the caret by the same numbering that survives a foreign render.

**Bounded at 60 steps** (`NOTE_UNDO_MAX`). A step is a word, not a character (below), so sixty steps is a longer reach back than a writing session asks for; a body is one string, so sixty of them is a few tens of KB at worst; and the whole history is held only for the open note and dropped the moment another one opens, so it cannot accumulate across a session. The oldest step falls off the front when the cap is reached, which is pinned.

**Where a step ends** is `noteHistBreak(prev,next,now,at)`: a run of ordinary characters is one step, ended by the space or line break that finishes the word; a run of single-character deletes is one step; `NOTE_UNDO_GAP` (700ms) of stillness ends any run; and anything that is not a single-character edit at a single point (a paste, a toolbar command, a list conversion, a body that arrived from elsewhere) is structural and always its own step.

**The note boundary** is one rule in one place. `renderNotes` resets the history whenever the open note's id differs from `noteHist.id` **or** the open note's body differs from `noteHist.cur.body`. Every foreign render passes through it, so switching notes starts fresh, and so does a body that arrived without passing the tracker.

**What happens if an undo lands while a foreign body arrives.** The same rule answers it, deliberately: the history describes one note at one body, so a body it has never seen means the history is stale by definition. `noteUndo` re-checks `noteHist.cur.body` against the live body before applying anything and, on a mismatch, refuses the step and re-seeds on what arrived. An undo can therefore never resurrect this device's pre-merge text over text that just came from the other device. The cost is real and accepted: a merge that changes the open note's body costs the reach back, and the user's next Ctrl+Z does nothing that time. Given the alternative is silently overwriting the other device, that is the right side to fail on. Pinned in both suites, including the case that matters most, a foreign render that does NOT change the body, which must leave the history fully usable (the 25s poll fires all day and agrees with the screen almost every time).

Applying a step is in-place: `n.body`, `ed.innerHTML=noteBodyHtml(...)`, `noteCaretSet`, then the same `notePatchRow` the input handler uses, then `save()`. No `render()`, so nothing outside the page moves and no other caret is disturbed, the same discipline typing already follows. `keydown` calls `preventDefault()` on all four chords (Ctrl+Z/Y, Cmd+Z, Cmd/Ctrl+Shift+Z), because without it Chrome would run its own native step as well and the two stacks would fight.

### 9.3 A dash and a space open a list; two spaces close it

`noteDashOpen` and `noteDashClose` hang off the same `keydown` branch as undo, and both are plain DOM work on the sanctioned shapes, never `execCommand`, so they behave identically whatever editing engine is underneath and are testable in jsdom as well as in Chrome. Each raises exactly ONE `input` event when it is done, so the body, the save and the undo history all see the whole conversion as a single edit: one Ctrl+Z takes a list back to the dash, which is pinned.

**It produces the dash list (`ul.dash`), not the round bullet.** The mark the user typed is the mark they get. Converting a typed dash into a round bullet swaps their punctuation for someone else's, and the way back out then reads as a substitution rather than as an undo. `ul.dash` is not a new list type: it is the exact shape the dash toolbar button already writes, the sanitizer already carries the class through by name (`noteScrubbed`'s `if(tag==='UL'&&n.classList.contains('dash'))`), and the stored shape is unchanged.

The trigger is narrow on purpose: the text from the start of the caret's line up to the caret must be exactly `-`, measured through `noteAsPlain` and `noteCaretGet` so the line numbering is the same fact the caret already counts by. A dash mid-line is text. A dash inside an existing list item is text too, and does NOT nest a second list, which would have introduced a shape the sanitizer and the merge have never seen.

The way out is a second space on an emptied bullet: the item is removed, a line reading `- ` is inserted after the list, items below it keep their own list (the list splits rather than losing them), an emptied list is removed entirely, and the caret lands after the space. The round trip is lossless, which is the point of choosing the dash list: what is left behind is exactly what was typed to get in.

### 9.4 The spellcheck underline: this one cannot be done

**Follow-up, 2026-08-12 (second report).** The behaviour was reported as "not working, and possibly worse", with a screenshot appearing to show faint red text UNDER the misspelled word, which would mean the app was drawing a mark of its own. **It is not, and it never was.** Nothing was shipped for this request in the first place, so there was nothing to revert; the previous commit answered it in this section rather than in code. Re-verified against the file rather than from memory, and all four facts are now pinned by tests:

- The string `spellcheck` appears exactly ONCE in `index.html`, on `#syncKeyIn`. There is no second occurrence, no runtime `spellcheck` write, and no toggle.
- No overlay, no decoration, no second layer of text. There is no element drawn over or under `#noteBody`, no `cloneNode` in the notes path, no mirror element, and no CSS Custom Highlight registration anywhere in the file.
- No red is reachable inside the editor. The only reds in the stylesheet are `--done`, `--today`, `--grad` and the progress-ring stops, all Monochrome-only, and none of them appears in any `#noteBody`, `.notepage`, `.notewrap` or `.ntools` rule. The editor's ink is `--txt`; its three highlights are `--panel`, `--ocean` and `--tasktile`; its two page textures are `--denim-rgb` (grey in Monochrome, dusty denim in Cloud blue) and `--ink-rgb`.
- The only thing the app draws below a line of text in this view is the Ruled page appearance, `#noteBody.pg-ruled`, a 1px hairline per line at 26% alpha, and it is grey or blue, never red, in both themes.

So the red in the screenshot is Chrome's own spell mark. On Windows, Chrome paints it as a dotted red run a few pixels under the baseline; at `line-height:1.7` it sits low and clear of the glyphs, and on a high-DPI display the dots resolve individually, which is what reads as "faint red text" rather than a squiggle. If the Ruled page style is on, that hairline sits in the same band and the two together look like a second line of something. This is a rendering-appearance question rather than a defect, and if the screenshot shows something these four checks do not explain, it is worth another look with the image to hand.

The rest of this section is unchanged and still stands.

Asked for: when a word gets the browser's red squiggle and typing carries on, the underline should clear once the word is committed with a space.

**It cannot be done as described, and nothing was shipped that pretends otherwise.** The squiggle is painted by the browser's own spellchecker in a layer the page cannot reach. There is no DOM API that exposes spell marks, no event when one appears or clears, and no way to address an individual mark; the CSS Custom Highlight registry, which IS readable, contains only highlights the page itself registered, and is empty here (pinned). The page's single lever is the `spellcheck` attribute, which switches the whole checker off for an element.

There is also a second problem underneath the first, worth stating because it changes what "fixed" would even mean: once a word is finished with a space and still carries a mark, the mark is usually CORRECT. Clearing it would hide a real signal rather than tidy a stale one. The case where the mark is genuinely stale, a partial word flagged mid-typing that becomes a real word when finished, is one the browser already re-checks at the word boundary on its own, and the app does nothing to prevent it: it never rewrites the editor DOM on a keystroke (`noteSerialize` reads `ed.innerHTML` into a detached div and stores a string; it never writes back).

**What was NOT done:** spellcheck was not disabled, anywhere, at any point. Both suites pin that: `#noteBody` carries no `spellcheck` attribute at all, so it inherits the browser default (on, measured as `ed.spellcheck === true` in Chrome), no script switches it off at runtime, and exactly ONE element in the whole file opts out, `#syncKeyIn`, where the value is a random key and every one of them would be flagged. That was already true before this commit and is now enforced.

**The closest achievable behaviour, offered rather than taken.** Toggling `ed.spellcheck` false and back to true forces Chrome to drop and redo every mark on the element, which would clear a stale mark on a finished word within a frame. It is not shipped, for two reasons. It repaints every mark on the element on every space, not the one word, so genuinely misspelled words visibly flicker off and back on as you type past them. And no harness here can verify it: headless Chrome does not run the spellchecker, and the marks are unreadable from the page in ANY Chrome, so the suite could never tell a working version from a broken one. Shipping unverifiable cosmetic behaviour into the most-typed-in surface of the app is the trade this project has consistently refused. If it is wanted anyway, it is about four lines in the same `keydown` branch the dash rules use, and it should be a per-device preference rather than always-on.

### 9.5 Undo and redo get buttons (2026-08-12, follow-up)

The chords from 9.2 do not exist on a phone or a tablet, which is where this app is mostly read. The toolbar now leads with two controls, Undo and Redo, and the history behind them is the one 9.2 describes, unchanged.

**Depth: 60 steps back (`NOTE_UNDO_MAX`), and as many forward as have been taken.** That is the pre-existing bound and it was already well past the ten asked for, so nothing needed raising. Worth being precise about what a step is, because it flatters the number: a step is a WORD, not a keystroke (`noteHistBreak`, 9.2), so sixty steps is sixty finished words rather than sixty characters. The forward stack is not separately capped; it can only ever hold what the back stack gave it. Both suites now drive a full ten-step run in each direction and assert it lands where it started: jsdom counts the run to the true bottom rather than assuming a depth, and `tests/viewports.js` does the same run through real taps on all four profiles, where it measures ten forward steps.

**One history, not two.** The buttons dispatch `note-step` to the same `noteUndo(ed, redo)` the `keydown` branch calls, with the same sync rule and the same re-seed. Pinned from both ends: a chord then a button are two steps of ONE stack, and each redoes the other's step. Nothing about the chords changed.

**The disabled state.** `noteStepsAvail()` returns exactly the conditions `noteUndo` accepts, including the 9.2 sync rule, so an enabled button always does something and a disabled one is never hiding a working step; `noteUndo` re-checks rather than trusting it. It is read at render time by `noteToolsHtml` and refreshed by `noteStepState()`, which the input handler calls on every keystroke (the cheap half of `noteToolState`: two attribute writes, no ancestor walks). The guard is the app's existing shape, a predicate computed from state at render time, the way the last-tab delete is guarded. It is expressed with the native `disabled` attribute rather than by omitting the control, which is a deliberate departure worth recording: the last-tab guard drops the button entirely, and that is right for a control whose condition changes twice a year, but Undo's condition changes on the first word of every note, and a toolbar whose buttons appear and vanish as you type would reflow the row under the pointer. `disabled` also carries into the accessibility tree, which an omitted element cannot do. Both buttons carry an `aria-label` and a `title`, so neither renders with an empty label; the glyphs are inline SVG, no emoji.

**The caret after a step, which is the half that makes it a feature.** `noteUndo` restores the caret to the absolute text offset the step was taken from, by the same numbering that survives a foreign render. The buttons needed one addition to make that true for them: `noteUndo` now focuses the editor before setting the range. A chord arrives with the editor already focused, but a press only keeps focus because mousedown is prevented, and a touch keyboard does not guarantee even that. Focus is taken FIRST and the range set after, because focusing afterwards collapses the selection to the start. Verified for real on all four profiles: after a tap of Undo the active element is `#noteBody`, the caret is at the character the step was taken from, and the next typed character lands there.

**The mousedown contract (Section 4) needed widening, and the reason is a genuine trap.** Chrome does not dispatch mousedown from a DISABLED button, so the old listener, bound to `#noteTools .ntb`, would never have run for a press on a dead Undo, and the press would have blurred the editor and dropped the phone keyboard for nothing. Two changes close it: `.ntb[disabled]` is `pointer-events:none`, so the press falls through to `#noteTools`, and the listener now prevents default across the strip rather than on the buttons alone (`#notePage` still keeps its default so its dropdown opens). That also covers presses landing on the strip's padding or on a separator, which were never covered before. The audit in `tests/viewports.js` had to learn the same fact: a disabled control is deliberately unhittable, so it is exempt from the hit test, though its size and its label are still audited.

**Geometry.** The strip carries two more buttons and a separator, twenty children in all. It wraps rather than overflows (`.ntools` was already `flex-wrap:wrap`), and every profile now asserts that nothing sits outside the box, that the box does not scroll, and that the page gains no horizontal scroll. On the coarse profiles both new buttons measure 44px, and the toolbar minimum is 44px across sixteen controls. The height cost, measured before and after: unchanged at 390px, 1024px and 1280px, and one extra 44px row at the 820px profile, which is the widest layout that still stacks the editor under the list.

## 10. Layout and navigation (new, 2026-08-12)

Six changes to how the app is moved around in. None of them touches sync, the merge, or either palette; no theme variable was added, changed or removed, and the two themes stay pixel-identical except where a change below moves something in both at once.

### 10.1 The rail collapses (Change 1)

`#railcollapse` in the brand row hides it; `#railshow`, a fixed button at the top left, brings it back. The state is device chrome on the SAME contract as the theme, deliberately: its own key `agora_dayplanner_rail`, applied as `data-rail="off"` on `<html>` by the head boot script before first paint, never a field on `state`. That is what makes "must not sync" structural rather than a promise: it cannot reach `stateSig`, so it can never trigger a push; it is not in `MERGED_KEYS`, so a merge has nothing to carry; and it never enters the planner blob at all, which the tests assert by searching the saved JSON for the key. Purely a CSS switch, so nothing re-renders when it flips.

**One trap, found by the viewport pass rather than by reading.** The collapsed rule was first written `grid-template-columns:0 minmax(0,1fr)`, which looks right and is not: `#rail` is `display:none` when collapsed, so it leaves the grid entirely and `#main` falls into the empty FIRST column, giving the board a width of zero. It is one column when collapsed, not a zero-width first one.

`#main` keeps a 56px left padding while collapsed so nothing is ever drawn under the restore button; the test asserts the board's left edge clears the button's right edge, rather than trusting the number.

**What it means on a narrow layout, which is the question asked.** Nothing, on purpose. Under 900px the rail is already a drop-down behind Menu; both controls are `display:none` there and a stored `off` has no effect, so a phone behaves exactly as it did. A second mechanism on the screen with the least room for either would be two ways to do one thing. Pinned at both narrow profiles.

### 10.2 Auto-hiding scrollbars (Change 2)

One rule set applied through `*`, so nothing opts in and a scroller written next year is covered the day it is written. A capture-phase `scroll` listener (capture because `scroll` does not bubble; passive so it can never delay a scroll) marks the scrolling element with `.scrolling` and drops it after 900ms of stillness.

**Why it cannot reflow, which is the whole design.** The gutter is reserved PERMANENTLY: the track keeps a constant width whether the thumb is visible or not, and only the thumb's colour changes. Nothing about the appearance costs layout, and no content can sit where a scrollbar was a moment ago because that strip was never content's to begin with. The tests measure this rather than assume it: every scroller on the page is asked for its box with and without `.scrolling`, and none changes.

**The Chrome trap, which cost a real bug.** Chrome understands BOTH `::-webkit-scrollbar` and the standard `scrollbar-width`/`scrollbar-color`, and when the standard properties are set it IGNORES the pseudo-elements and falls back to its own thin overlay, which reserves nothing and lets content sit under the thumb. The first version set both unconditionally and silently lost the gutter in Chrome. The Firefox fallback is now gated behind `@supports not selector(::-webkit-scrollbar)`, so the two mechanisms never meet.

**Platforms that draw them differently.** Styling `::-webkit-scrollbar` opts Chrome, Edge and desktop Safari out of overlay scrollbars and into a classic reserved gutter, so macOS behaves like Windows and pays a permanent 10px per scroller; that is the price of the no-reflow guarantee and it is paid deliberately. Firefox takes `scrollbar-width:thin`, which reserves a constant gutter the same way. The one case the page does not control is the TOP-LEVEL page bar on a touch device: mobile browsers draw a transient overlay there that no page can opt out of. It costs no layout either, so the no-reflow half holds everywhere; only the "never under content" half is the platform's call, and only for the page itself. The viewport pass asserts each case as what it is rather than forcing one answer.

**Nothing becomes unreachable without hover.** The thumb appears for every way of scrolling, not just the ones a pointer can do: wheel, trackpad, touch drag and the keyboard (arrows, Page Down, Home) all raise the same `scroll` event. Hover is used only as an EXTRA, to surface the thumb on a pointer device so it can be aimed at and dragged; a touch device needs none, because a finger scrolls the content itself and never needs to hit the bar. No rule gates `.scrolling` behind hover, which a test pins.

The always-visible scrollbar block that used to sit near the top of the stylesheet is gone, and the day strip's `display:none` opt-out with it: one mechanism, no exceptions. The strip's bottom padding drops by the gutter it now reserves, so that row is the height it always was.

### 10.3 The logo resets the view (Change 3)

The mark and wordmark are now one real `<button class="brandbtn">` with a name, routing to `case 'home'`.

**What the reset includes:** `view` to board, `floatMode` off, `boardOffset` to 0 and `stripDay` to null (today in view at both widths), `calSel`/`calOffset` cleared, `noteSel` cleared, and the memory-only `ui.sel`, `ui.noteQ`, `ui.peek` and `ui.northOn` put back to rest.

**What it deliberately leaves alone:** every item of planner data (asserted by comparing days, notes, floats, habits, week, focus, bin and tombstones byte-for-byte across the press, in both suites); the sync connection and any push already in flight; the theme; the rail's collapsed state; and the persisted panel collapses. `stateSig` is unchanged by it, so it pushes nothing of its own.

**In-progress edits are committed, not dropped.** An open inline add row is committed the way tapping outside it already does, and `flushSave()` forces the 400ms debounce so a note body or title still inside it is written before the view changes under it, which a test drives through a real keystroke. `flushSave` is what `syncCycle` itself calls before a merge, so it can only help a cycle land, never interrupt one. It is a view reset, never a reload; the tests assert the source contains no `location.reload`.

### 10.4 Tab reorder by tap (Change 4)

See risk 12 above, now closed. Nothing further to add here.

### 10.5 This week collapses with content (Change 5)

The header always carries `week-toggle` and always draws a chevron, since it can now always act. With items the persisted per-device `settings.weekOpen` governs, exactly as `habitsOpen` does for Habits; empty, it is the same memory-only peek the other panels get, and opening an empty panel clears a remembered collapse so the first item added does not land under it.

`weekOpen` rides `VIEWSET` beside `habitsOpen`, so a manual Pull never imports another screen's collapse states, and settings are not part of `stateSig`, so collapsing pushes nothing. Both facts are pinned, along with a fresh boot coming back collapsed with the item still held. True north is untouched by this change and keeps its pinned-open rule.

### 10.6 True north rests (Change 6)

At rest the panel is the statement and nothing else: the add field and the Set aside archive are drawn only while the panel is the one being used.

**Two flags, one meaning each, deliberately not merged.** `ui.peek.focus` is the old one and is untouched: it opens an EMPTY panel so something can be added, and is dropped the moment the panel holds a statement. `ui.northOn` is new and gates the working parts only. The first attempt merged them and broke a rule it had no business touching: emptying the panel left it hanging open instead of folding to its header bar. Keeping them apart is what lets the empty-panel collapse rule and the pinned-open rule both survive unchanged. Neither flag can reach the statement, so no value of either hides a held statement, and both are memory-only, so nothing about them loads, saves or syncs.

**Exactly what shows and hides it.** SHOWS: a press anywhere on the panel (`#fpanel` carries `north-open`, and a press on a row's own button leaves the panel active rather than toggling it off, since the case is idempotent), and setting a statement, which keeps the field under the user's hands for a second one. HIDES: a press anywhere outside the panel, handled on the press rather than on the input's blur so a tap on bare canvas closes it too, and Escape. Both call `renderFocus()` alone, never `render()`, so nothing else on screen moves and no other caret is disturbed.

**A first statement can always be added.** With nothing held the panel is a header bar carrying a chevron and a "not set" tag, and its header toggle opens it with the add field right there. That path is unchanged and is pinned end to end: empty, open, type, set, and the field is still there for the next one.

It keeps a rim, and the rim is sized to the job per theme: blue keeps the palette hairline `#9BBBD4` it was always drawn with (1.86:1 on the backdrop, the same edge it had before at 1.84, so blue did not regress), while mono's `#40404A` is a real 3:1-clearing boundary because in a near-black rail the edge is the whole difference between a card and a cut-out. Mono's rim is asserted at 3+; blue's is asserted to be unchanged rather than held to a bar its existing design never met, which is a deliberate choice not to invent a threshold retroactively.

### 12.2 One size across the rail

`.navbtn` goes 13.5px to **19px**, matching the held statement, so the four nav labels and the statement read at one size. 19px was already a step on the scale; nothing new was introduced.

**The convergence had to go up, and the reason is worth keeping.** The brief asked whether the new backdrop rescues the ratio enough to shrink the statement to the nav size. It does not, and the framing needs one correction: **contrast is a property of two colours and does not move with type size.** Mono's red measures 3.65:1 on `#F6F6F7` at 19px, at 13.5px, at any size. What size changes is which bar applies, and there is no size at which 3.65 clears 4.5. So there is no "smallest size that clears" to offer: the statement is legal as WCAG large text and illegal as normal text, full stop. The large-text floor at weight 700 is 14pt = **18.66px**, which makes 19px the smallest compliant step, and the scale jumps 17 to 19 with nothing between, so no compromise size exists either. Lowering the statement to 13.5px would have meant shipping a mono AA failure and relaxing four assertions to hide it. Raising the nav costs nothing: at 19px the labels are still weight 500, so they are still normal text and 4.5 is still their bar, and both palettes clear it, resting 4.85 blue and 7.92 mono, active 10.35 and 10.95. Under 900px the nav group is already an `overflow-x:auto` strip, so the extra width costs scroll, not page overflow.
